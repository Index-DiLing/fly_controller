## 观测 1：`拒`(decodeRejects) ≈ 0.67/发帧 —— 已加修复（待重烧复测）

| 量 | 实测 |
|---|---|
| 1m 日志（13:52，20s） | 拒/发帧 = **0.665**（109/164），跨 14min 三份日志 0.61–0.67 |
| 4m 日志（14:00，61s） | 拒/发帧 = **0.669**（338/505） |
| v1 对照（10-17） | `拒 ≡ 0`，且 收字节/收帧 = 8.00 整 |
| 空闲 7s（13:45） | 拒/收字节/收帧/发帧 四个计数**全部冻结** |

判读：不是 RX 线噪声（空闲不增长），也不是整帧回环（0.67 字节/轮 ≪ 13B 帧长）；是**飞控发 D0 时半双工换向/PD8→PD9 串扰在 RX 上注入的 1–3 字节短瞬变**，集中在帧间静默相。`采信拒=0、采纳==收帧` ⇒ 功能零损伤。

**修复（2026-10-18 已实现，未上板复验）**：
- `app/link/app_link_thread.hpp`：D0 发送窗口 `[发送起点, 空中结束 + guard + 2ms]` 内到达的 RX 突发**直接丢弃**，不进解析器、不计 `拒`；单独累计 `txWinBursts/txWinBytes`；
- 新增 `[Lk2]` 1Hz 短诊断行：`[Lk2] U0..3=x/x/x/x 上行丢=x% tx窗RX=xB`。
- 复测判据：`拒` 不再增长；`tx窗RX` ≈ 5–6 B/s（与原先 5.45/s 的杂散量级一致）。
- 注意：这是**实现层**的过滤，不改变线上协议；发送窗口内半双工下本来就不可能有合法对端数据。

## 观测 2：上行帧率 31.9–32.0/s（期望 33.33/s，≈3.7% 帧缺失）—— 观测中

| 量 | 1m 日志 | 4m 日志 |
|---|---|---|
| 收帧速率 | 31.95/s | 32.00/s |
| 轮长（按 发帧+发失败 算） | 119.8ms | **120.3ms（正常）** |
| 上行缺失 | 4.3% | **3.75%** |
| 发失败(D0 放弃) | 3/167 = 1.8% | 2/507 = 0.4% |
| 采信拒 | 0 | 2 |

判读：
- 轮长正常；**1m→4m 无改善，排除近场饱和**（子代理报告里的“轮长 125ms”是误算，已更正）；
- 缺失帧既不计 `拒` 也不计 `采信拒`（根本没成帧）；
- 协议冗余使影响有限：U0/U1 都带杆量、U3 丢走兜底 D0、控制仍按最新值执行；
- 可能原因（待诊断）：RC 侧“迟到 >3ms 跳帧”/`radio_send` 因 AUX 忙失败/空口碰撞；
- **下一步**：重烧后看 `[Lk2]` 的 `U0..3` 增量——
  - 若某个位置明显偏低（例如 U3），查 RC 侧 `ul_skip_late/ul_fail`（可临时在 UI/日志暴露）；
  - 若四个位置均匀缺失，查空口/RC 任务抖动/距离。
