# 链路层 v2 · 第一轮：现状梳理、问题分析与设计思路

> 2026-10-17 · 只读侦察 + 方案建议，不含代码改动。
> 范围：飞控端 `E:\STM32Code\fly_controller`、遥控器端 `E:\ESP_PROJECT\controller`。
> 依据：两端源码逐文件核对 + `.tmp_analysis/audit/*` + 两台设备实测值（8B=16.5ms 等）。
> 结论口径：**TDMA 保留，帧层/语义层/同步层整体重做**。

---

## 0. 结论速览

1. **现状骨架**：超帧 120ms = 5×24ms；遥控器（主端）槽 0–3 上行 33.3Hz，飞控（从端）槽 4 下行 8.33Hz。11 种"类型即长度"的定长帧（整帧 4–20B），1B 帧头 `(TYPE<<4)|SEQ`，CRC-8，无长度/版本/会话/确认位图。
2. **物理预算（实测）**：单帧成本 `F(n) ≈ 13.5 + 0.38·n` ms（8B=16.5、12B=18.2、20B=21.2、32B=25.4）。一帧 = 一个空口包 = 一次连续 UART 写，中间停顿 >3 字节时间即裂包。半双工、无 ACK/重传/FEC/CAD、RSSI 不可读。**24ms 槽已接近物理下限（16.5+guard），33.3Hz 上行不是历史包袱，而是射频决定的**。
3. **真正要换的不是"哪些帧"，而是三处结构性耦合**：
   - 帧层刚性：类型即长度、无长度/扩展/分片 ⇒ 命令挤控制、ACK 挤遥测、GPS 20B 顶格；
   - 可靠性与调度耦合：准入拒绝 = 丢槽、杆量历史只采信才更新、OffGrid 不重锚 ⇒ 可永久自锁；
   - 时间基准错误：8ms 线程时刻当到达时刻、窗口用单一 16.5ms 常量、无槽号/会话 ⇒ 下行窗口贴边、重启后 49% 死链。
4. **建议方向：TDMA-Bundle（时分载波 + 统一 bundle 帧 + 捎带确认 + 会话/能力）**。保持 120ms/5×24ms 与 4 上 1 下；每槽一个可变长 bundle；控制量每帧必带，命令/制导捎带；下行核心状态每帧必带，其余按优先级分片；TC 用 ISR 时间戳 + 帧内槽号做"解码式同步"。预算：UL 12B（18.1ms）/带命令 15B（19.2ms），DL 16–20B（19.6–21.2ms），超帧占空 ~77–82%。

## 1. 物理层预算（链路层设计的天花板）

| 项 | 值 | 含义 |
|---|---|---|
| 模块 | E220-400T30S，透传模式，信道 23（433.125MHz） | 两端 ADDR/KEY 均为 0，无身份隔离 |
| 空中速率 / 串口 | 62.5kbps / 57600 8N1 | 串口上限硬约束：≤1.25×空速 |
| 分包 | 32B | **单帧硬天花板 32B**；>32B 被模块切开，定长解析必崩 |
| 单帧实测成本 | `F(n)=13.5+0.38n` ms：8B=16.5、12B=18.2、20B=21.2、32B=25.4 | 固定开销 13.5ms 主导；边际仅 ~21kbps（配置 62.5k 的 1/3，须复测） |
| 断帧 | URXT=3 字节时间（@57600≈0.52ms） | 一帧必须一次连续写完；中间停顿即裂成两包 |
| 半双工 | 射频 TDD，无 CAD/LBT（LBT=0），模块无 ACK/重传/FEC | 冲突与可靠性全部由上层承担 |
| 时间同步 | 模块无时间戳/信标/WOR | 相位只能靠"帧到达时刻 + 帧内信息"估计 |
| 方向切换 | 发完忙一整帧（8B≈16.5ms）+ guard 3ms | 最小可靠时隙 ≈20ms；24ms 是合理值 |
| 当前占空 | 实测 AUX 低 69% | 安全上限约 70–80% |

**推论**：每超帧（120ms）用户字节预算约 **80–100B**；1 帧/槽是硬事实（同槽发两帧必被合并或切开）。控制率天花板 ≈40Hz，但要留 16B 以上帧就只能是 33Hz 左右。

## 2. 现状：分时复用

```
超帧 120ms = 5 × 24ms
槽0     槽1     槽2     槽3    │  槽4
RC      RC      RC      RC     │  FC（唯一下行窗口）
上行每槽 1 帧，33.3Hz          │  下行 1 帧，8.33Hz
```

### 2.1 发送侧（遥控器主端）
- 独立任务 `fc_link_task`（core0、prio 7）用 `esp_timer` 绝对时刻跑 24ms 网格：先粗睡到边界前 1ms，再 50µs 步进忙等（`fc_link.c:207-246`）。
- 每个上行槽**只发一帧**，按优先级选：命令队列非空 → `UP_CMD`；槽 3 且有制导 → `UP_SETPOINT/UP_VEL/UP_MOTOR`；否则 `UP_CTRL`。
- 迟到 >1 超帧才重对齐；迟到 <120ms 会连续补发，帧间隔 <18ms，被飞控 `TooSoon` 拒（`fc_link.c:216-242`）。

### 2.2 接收侧（飞控从端）
- 锚点 = 收到主端帧时的**本地处理时刻**（`linkMicros()`，8ms tick 上取值，`app_link_thread.hpp:230-237`）。
- 只有 `SEQ % 4 == 3`（槽 3）的帧才"开窗"；窗口开启 = `anchor + (24000−16500) = anchor+7500µs`；关闭 = 开启 + 24ms（`dlx_link_sched.hpp:350-354`）。
- 发车条件：窗口已开 ∧ 距最后一帧有效上行 ≥ guard 3ms ∧ 未静默。
- 相位容差 = slot/4 = 6ms；连续 2 槽无有效上行 → `LINK_DESYNC 0x204`，静默（只收不发）；连续 2 帧通过准入才恢复（`dlx_link_sched.hpp:317-321,375-390`）。

### 2.3 关键缺陷
1. 锚点是软件处理时刻，量化 0–8ms，而容差只有 6ms；两端晶振漂移每 3–7 分钟还会跳一拍。
2. 窗口只减掉一个固定 16.5ms，没算"本帧多长"与量化；12B 以上下行帧余量为负或贴边。
3. OffGrid 只计数、不重锚；遥控器重启后约 49% 概率永久失锁（仿真），只能等时基回绕。
4. 窗口关闭时间 = 开启+槽长，比下一上行帧还晚；代码不再检查上限，靠时序预算"运气"。

## 3. 现状：帧种类与含义

### 3.1 通用格式
```
B0        = (TYPE<<4) | (SEQ & 0x0F)
B1..N-2   = payload（LSB-first 位打包，字段可跨字节，小端）
BN-1      = CRC-8/ATM（poly 0x07, init 0x00，覆盖 B0..N-2）
```
- 帧长由 TYPE **唯一决定**，无长度字段；坏帧只前进 1 字节重同步。
- SEQ 4bit，方向内自增 mod 16；上行 33.3Hz ⇒ 480ms 回绕。
- 上下行共用同一套封帧，仅靠类型 nibble + 准入掩码区分方向。
- 单帧最大 20B（DL_GPS），最大负载 18B。

### 3.2 下行（FC → RC）

| TYPE | 名称 | 整帧/负载 | 实际节拍 | 内容与语义 |
|---|---|---|---|---|
| 0x1 | DL_ATT | 12B / 10B | ≈240ms（4.17Hz） | 四元数虚部 3×12b、机体速度 3×i8、status/error、arming、mode |
| 0x2 | DL_SYS | 14B / 12B | 480/480/960ms（≈1.56Hz） | 位置 x/y/z 12b、电流/电压、四路 DShot 11b |
| 0x3 | DL_GPS | 20B / 18B | 设计 1.92s；GNSS 关时**整槽空发** | 经纬度/海拔/地速/航向/星数/fix/hdop |
| 0x4 | DL_STATE | 9B / 7B | ≈480ms（2.08Hz） | 状态机镜像、failsafe、health、上下行丢包、RSSI（恒 0） |
| 0x5 | DL_ACK | 4B / 2B | 事件触发，占当窗唯一下行帧 | op + result；**帧头 SEQ 回显被应答的上行 SEQ** |

下行轮转：`d%16→GPS`、`d%4→SYS`、`d%2→STATE`、其余 `ATT`，ACK 严格优先且不推进轮转。

### 3.3 上行（RC → FC，同一槽只能选一种）

| TYPE | 名称 | 整帧/负载 | 触发 | 内容与语义 |
|---|---|---|---|---|
| 0x8 | UP_CTRL | 8B / 6B | 默认每槽，33.3Hz | roll/pitch/yaw 11b(±1023)、thr 11b(0..2047)、flags |
| 0x9 | UP_CMD | 4B / 2B | 按键事件，连发 1–3 帧 | op（表 21 条，实际接通 8 条）+ arg |
| 0xA | UP_VEL | 5B / 3B | 仅槽 3，VEL 模式，8.3Hz | 三轴世界系速度 i8 @5cm/s |
| 0xB | UP_POS | 6B / 4B | **从未发送** | x/y i16 dm |
| 0xC | UP_SETPOINT | 5B / 3B | 仅槽 3，ALT 模式，8.3Hz | 绝对高度 i16 cm + ALT_VALID |
| 0xD | UP_MOTOR | 8B / 6B | 仅槽 3，TEST 模式，8.3Hz | 四路 DShot 11b |

**结构性含义**：一槽一帧 ⇒ 命令与杆量互斥（ARM 三连发 = 72ms 无杆量）；ACK 与遥测互斥（连续 ACK 把 ATT 空档拉到 720ms 以上）；制导帧缺一拍就是 120ms。

## 4. 现状：两端处理方式

### 4.1 飞控端
```
E220 UART RXNE → 256B 环形缓冲
   → 8ms 定时器信号量唤醒链路线程（prio 24）
   → 最多读 64B → tryDecode() 自定界（坏帧 +1B）
   → FrameAdmission::admit()  （方向/类型 / 最小间隔 18ms / SEQ 窗口 4 /
                                字段量级 / 命令表 / 杆量步进 ≤0.25）
   → 只有 Ok 才 SchedSlave::onMasterFrame() 重锚
   → 分发：ControlInput(LockedCell) / 命令 MPSC / ACK 环 / Health / LinkStatistics
发送：窗口内 → ACK 优先 → DownlinkPlanner 轮转 → sendRaw() 阻塞 TXE 轮询
```
- 命令 → Request（带 wireSequence/op/safetyEpoch）→ 控制线程 500Hz 执行 → 结果回 SPSC → 下行 ACK。
- 失效保护：控制输入 2s 新鲜度；Armed 且非 Manual 且有垂速 → 缓降；否则停止输出。配置里的 300/1000/2000ms 三级与 `kMinValidUplink=8` 都没有消费者。

### 4.2 遥控器端
```
fc_link_task（24ms 槽）：
  wait_slot → 排空 UART（每次≤32B，环 64B）→ fc_frame_next() 切帧
  → 方向/CRC/字段语义准入 → 按帧类型更新 tm.*（各自 valid+时间戳）
  → fc_publish() 合成快照 → rc_state → UI / rc_flight
  → 槽 0..3 选一帧发（命令 > 制导(槽3) > CTRL，CTRL 单帧斜率限制）
  → 槽 4 每 1ms 轮询收下行
```
- 失联：500ms 无任意有效下行 → NO LINK；`fc_valid`（曾经收到）与 `fc_fresh`（仍新鲜）分离。
- 遥控器侧**没有任何失效保护动作**；失联时仍按最后模式发制导帧、按最后 arming 积分油门。

### 4.3 可靠性 / 观测现状

| 机制 | 现状 |
|---|---|
| ACK | 仅 UP_CMD 有；ESTOP 无 ACK；无命令 ID、无重传定时器 |
| 重传 | 无；危险命令固定连发 3 帧（非幂等） |
| 去重 | 仅 SEQ 相同判重；丢满 16 帧会被误判 |
| 丢包统计 | 上行用累计值且丢槽数饱和 15；下行假设每超帧必有 1 帧；GPS 空槽算丢包 |
| 失效保护 | 飞控只有 2s 一级；遥控器无动作；DL_STATE.failsafe 恒 0 |
| 观测 | 准入拒绝只有总数；无拒因、无逐帧 ack、无 RSSI；故障时统计反而显示正常 |

## 5. 设计层面的问题（为什么必须换）

| # | 问题 | 后果 |
|---|---|---|
| 1 | **类型即长度**：加字段/加长帧必须动全表，且旧端会把扩展位当假帧整帧拒（DL_STATE 7 个保留位已被旧 RC 用作准入） | 任何演进都变成两端同时烧；无法渐进 |
| 2 | **无长度/无分片**：GPS 20B 已顶到 24ms 槽的极限；日志/参数/黑匣子没有承载手段 | 下行数据率被锁死；将来加功能必然再次爆槽 |
| 3 | **一槽一帧、控制/命令/ACK 互斥** | 命令期间控制停更；ACK 挤掉遥测；33.3Hz 名义上很高，实际有效控制更新更低 |
| 4 | **可靠性语义塞在准入里**：拒绝 = 丢槽、杆量历史只在采信时更新 | 一次丢帧可永久自锁；0x204 只是症状 |
| 5 | **无会话/身份/版本**：CRC8 只能检错；同频另一套设备可注入合法帧；遥控器重启后旧历史与新 SEQ 分叉 | "重启必须双端同时重启"；安全边界不清 |
| 6 | **时间基准错误**：8ms 线程时刻当到达时刻、窗口用单一 16.5ms 常量 | 窗口余量为负、周期性 OffGrid、下行丢包不可解释 |
| 7 | **轮转是静态取模**：d%16/d%4/d%2，长度与节拍强耦合 | 接收端只能用"每帧类型一个超时常量"兜底；改节拍就误判 |
| 8 | **两端各写一份常量**，靠注释与黄金向量人工对拍 | 协议一改就漂移；测试脚本在两端都缺失 |

## 6. 新思路：TDMA-Bundle

### 6.1 原则
1. **TDMA 不动**：半双工 + 无 CAD/无 ACK + 一帧一包，决定必须时分。保留 120ms = 5×24ms、4 上 1 下、33.3Hz 上行。
2. **帧层唯一**：所有方向、所有用途都是同一种 bundle 帧；用"块（block）"表达语义。
3. **控制永远是第一公民**：每个上行 bundle 必带最新杆量；命令/制导/确认只是捎带。
4. **确认是常态**：每个 bundle 头部带对向帧的 ACK 位图，不再需要独立 ACK 帧。
5. **同步靠解码，不靠猜**：帧内带槽号/超帧号，飞控收到一帧即可重建相位；ISR/DMA 打到达时间戳。
6. **准入分层**：帧完整性、会话、序号、语义四层分开；语义拒绝不影响调度相位。
7. **能力与版本在线协商**：一份机器可读的能力块，取代两端手抄常量。

### 6.2 分时结构（默认 profile）
保持 5×24ms；槽 0–3 上行，槽 4 下行。可选 profile（由能力帧协商、超帧边界生效）：
- `NORMAL` 4U+1D / 120ms：上行 33.3Hz、下行 8.33Hz（默认）。
- `TELEMETRY` 3U+2D / 120ms：上行 25Hz、下行 16.7Hz，用于日志/参数/GPS 批量传输。
- 恢复期：遥控器重启后新会话直接以 NORMAL 起步，飞控 1 帧内重锁，不需要特殊模式。

### 6.3 帧格式（示例，字段可再压缩）
```
B0   SYNC 0x5A
B1   VER(2) | KIND(2) | LEN(4)        // KIND: CORE / CMD / GUIDE / TLM / CAP / LOG
B2   SLOT(2) | SFN(6)                 // 槽号 0..3，超帧号 mod 64（≈7.7s）
B3   SEQ8                              // 方向内连续帧号
B4   ACK8                              // 对向最近 8 帧的接收位图
B5..  payload（块，按 LEN 变长）
B?-2 CRC-16/CCITT
```
- 头部 5B + CRC 2B = 7B；**上行建议定长 12B（仅控制）/15B（带命令）**，下行 16–20B 可变。
- 定长上行 + 帧内 LEN 让飞控能精确计算"本帧耗时"：窗口 = 末字节到达时刻 + 槽长 − (F(n)+d_rx)，替代固定 16500µs。
- 块用 1B 块头（块类型 3b + 长度 5b）串联；未知块按长度跳过 ⇒ 旧端不会因扩展位整帧拒收。

### 6.4 上行语义
- **CORE 块（每帧必带）**：roll/pitch/yaw/thr（沿用 11b 量化）+ safety flags（ESTOP/ARM 请求等锁存位）+ 模式意图。
- **CMD 块（可选，≤3B）**：cmd_id(6b) + op(5b) + arg(8b)。重传同一 cmd_id 直到被 ACK；飞控按 cmd_id 幂等去重 ⇒ ARM 连发不再产生 REJ_STATE 歧义。
- **ESTOP 不再是一次性命令**，而是 safety flags 的锁存位：每帧重复，直到 ACK 或 disarm。这比"发一帧然后祈祷"安全一个量级。
- **ACK8** 让遥控器逐帧知道哪几帧到了；配合 DL 的 ACK8，两端都有真实的丢包结构。

### 6.5 下行语义
- **CORE 块（每帧必带，约 8–9B）**：姿态 3×12b + mode/arming/health + 三轴速度 + failsafe 等级/原因。⇒ ATT/STATE 不再分帧、不再被 ACK 挤掉，下行 8.33Hz 始终有状态。
- **TLM 块（按优先级/老化）**：SYS、GPS、命令结果、连接质量，按块分片（1B 分片头：流 2b + 序号 3b + first/last）；每超帧剩余字节装片。
- **CAP 块（低频）**：协议版本、支持的块/命令、槽表、ack 窗口、failsafe 阈值、当前 profile。
- 分片流用上行 ACK/分片位图做 ARQ-lite；日志/参数/黑匣子因此有了可靠通道（数据量受 150B/s 级带宽限制，大文件仍建议地面有线）。

### 6.6 同步、会话与重启
- 飞控在 UART ISR/DMA 完成中断里为每字节打 `DWT->CYCCNT`，帧末字节时刻 = 到达时刻（把 0–8ms 量化降到 ~10–50µs）。
- 帧内 `SLOT+SFN` 让飞控**一帧重建相位**：`槽起点 = 到达 − F(n) − d_rx`；不再需要"落在网格上才锚定"。
- 相位跟踪：小误差按 1/4 增益缓移，大误差（重启/长断链）直接按 SFN 重锚；无需等 35.8 分钟。
- 会话：遥控器每次启动生成 8b session；飞控看到新 session 即清序号/杆量历史并重锚。**重启不再需要双端同时断电**。
- 身份：E220 写唯一 ADDR/KEY（地面一次性），帧内再加 session；双保险。

### 6.7 准入分层
| 层 | 判据 | 失败动作 |
|---|---|---|
| L0 帧完整性 | SYNC/LEN/CRC-16 | 丢弃，+1B 重同步 |
| L1 会话/版本 | session 已知、VER 兼容 | 丢弃该帧；版本不兼容进"最小安全模式" |
| L2 序号/重放 | SEQ 窗口、去重 | 丢弃，但不影响相位 |
| L3 语义安全 | 杆量步进、模式合法性、命令白名单 | **夹取/降级/拒绝该块**，仍更新相位与统计 |

⇒ "被语义拒绝"永远不再等于"丢槽"，从根上消除 0x204 自锁类故障。

### 6.8 观测

## 9. 风险与必须先测的量（第二轮开工前）

1. **16.5ms 是真空中时间还是模块固定处理延迟？** 实测边际 ~21kbps 与配置 62.5kbps 差 3 倍；若实际空速不是 62.5k，整个槽预算要重算。用 `txProbe` 在 8/12/20/32B × 各空速档重测。
2. **FC 自检 21ms 是冷启动还是稳态？** 若是稳态，24ms 槽装不下 16B 以上下行帧，A 方案要缩小 DL 或改 32ms 槽。
3. **收→发切换时间**（FC 收完到能发）与 **发→收切换时间**；决定窗口起点与 guard。
4. **模块电压/功率/温度**：30dBm 近场饱和、长时间 80% 占空的热与电流。
5. **两端时钟漂移与 SFN 回绕**：长时间只收不发后能否一帧重锁（仿真 + 台架）。

## 11. 备选实验：把 E220 当"串口转发器"（400B 缓冲 + 自由竞争）的评估

**假设**：利用模块 400B 串口缓冲，双方按需写 UART，让 E220 自己挑空闲时段发送；不做 TDMA，帧设计放开。

**结论**：值得台架验证，但不建议直接作主飞行链路。三个前提不成立：

1. **400B 缓冲不是 MAC**：模块不感知对端、不做公平排队、不提供送达反馈；缓冲满时静默丢包，没有给 MCU 的"buffer full"信号。它只是 UART→空口的弹性缓冲。
2. **"挑空闲"只有 LBT**：置 `REG3[4]`（`AT+LBT`）才有效（`dlx_e220_config.h:194`）。手册语义是"发前听一下、忙则等、**最长 2s 后强制发射**"，没有随机退避、没有 ACK、没有优先级。半双工下两个节点同时判空闲仍会同时发、双双丢包；2s 强发意味着极端拥塞下时延无上界。
3. **承载能力要按"包/秒"算，不是字节/秒**：`F(n)=13.5+0.38n` ⇒ 8B=60.6 pkt/s、12B=54.9、16B=51.0、20B=47.2。现状 33.3 上行 + 8.33 下行 = **41.6 pkt/s（占空 69%）**。自由竞争要留 2–3 倍余量，安全区约 **15–20 pkt/s 总量** ⇒ 控制率只有 12–15Hz。更直观：上行周期 30ms，而单包 16.5–21ms，留给"等对向发完"的预算只有 9–13ms。

**更值得试的简化**：把试验目标从"去 TDMA"改成"去全局同步"——**自时钟 2:1 突发 TDD**：遥控器连发 2 帧上行（gap 3–5ms）→ 飞控收到第 2 帧后立即回 1 帧下行 → 遥控器收到/超时后再发下一对。没有绝对 24ms 网格、没有相位锚点、没有窗口常量、没有 OffGrid；任何时刻只有一方在发，天然无碰撞，下行就是回执。预算：12B×2 上行 + 16B 下行、gap 3–5ms ⇒ 周期 65–71ms ⇒ **上行 ~28–31Hz、下行 ~14–15Hz、占空 79–84%**。

**台架矩阵**：

| 试验 | 拓扑 | 变量 | 否决线 |
|---|---|---|---|
| E0 | 标定 | 空速档 × 帧长 8/16/24/32 | 先确认 62.5k 是否真生效；若实际是 19.2k，全部预算重算 |
| E1 | 自由竞争 + LBT | 总包率 5/10/20/40 pkt/s；LBT 0/1 | 40 pkt/s 下送达 <99.9% 或 P99 >50ms ⇒ 不能作主链路 |
| E2 | 自时钟 2:1 | gap 3/5/8ms、N=1/2 | UL <28Hz 或 P99 >10ms ⇒ 退回带同步 TDMA |
| E3 | 400B 突发 | 一次写 400/800B | 明确溢出/顺序行为，作为批量下载模式前提 |

**400B 缓冲的正确定位**：不是日常串口管道，而是**批量下载窗口**——进入下载模式后一方连续灌 400B（模块切成 ~13 个 32B 包，约 325ms），另一方只收不发，结束回 ACK。日志/参数/黑匣子走这个模式，比硬塞进 8.33Hz 下行现实。

## 12. 帧计数分时（轮次 TDD）：把"同步"从时间轴挪到帧计数

**先澄清现状**：现网不是帧计数，而是**绝对时间 TDMA**——遥控器用 `esp_timer` 跑 24ms 网格，飞控把"收到帧的本地处理时刻"当锚点，再用 `anchor+7500µs` 开窗。帧计数是另一种模型，下面单独设计。

**模型**：一轮 = n 帧上行 + m 帧下行；双方只靠"帧序号位置 + 超时"对齐，不用绝对时钟。

```
轮次 R:
  U0 ─3ms─ U1 ─3ms─ U2 ─3ms─ U3(位置=n-1) ─guard─ D0 [─3ms─ D1] ─idle─ U0(下一轮)
  ↑遥控器发                                    ↑飞控触发             ↑遥控器等 m 帧/超时
  |<------------- 上行突发 ------------>|      |<-- 下行突发 -->|     |<-- 空闲 -->|
```

**关键技巧：现有 1B 帧头就够**。帧头 `TYPE(4)|SEQ(4)` 的 `SEQ mod n` 就是帧位置（n 取 2/4/8，16 是它们的公倍数，回绕不影响位置）。飞控看到 `SEQ mod 4 == 3` 就知道"这是本轮最后一帧"——和现网 `seq%4==3` 同一个判据，但**语义从"时间栅格"变成"帧位置"**，不再需要相位/网格/窗口。

**触发与超时层级（必须严格排序）**：
1. 飞控收到位置 n−1 的帧 → 等 guard（3–5ms）→ 发下行；
2. 位置 n−1 丢了 → 飞控按"已知剩余帧数 × 帧间隔 + margin"超时触发；位置从帧头解出，不会提前发；
3. 遥控器发完 n 帧 → 开接收窗等 m 帧，超时 `T_dl`（如 60ms）；
4. 必须满足：飞控的上行等待超时 < 遥控器的下行等待超时，否则两边会互相抢。

**恢复（不死等）**：
- 遥控器连续 2 轮收不到下行 → 发 `PING`（复用现有 UP_CMD）→ 飞控回 `ACK` → 双方重置轮次状态；
- 飞控不主动探测（避免双向同时探测碰撞）；它掉电重启后进"捕获态"，只收不发，等下一个 `SEQ mod n == 0` 的轮次首帧再入网；
- 遥控器重启 → SEQ 归零、session 变化 → 飞控看到位置 0 或 session 变化即重锁，**不需要双端同时断电**。

**n:m 预算（8B 上行、下行按类型，gap 3ms，占空按 70–75% 留 idle）**：

| n 上 / m 下 | 下行帧 | 轮长 | 上行率 | 下行率 | 占空 |
|---|---|---|---|---|---|
| 4 / 1 | 12B | 120ms | 33.3Hz | 8.3Hz | 70% |
| 4 / 2 | 12B+14B | 140ms | 28.6Hz | 14.3Hz | 74% |
| 3 / 2 | 12B+20B | 120ms | 25.0Hz | 16.7Hz | 74% |
| 4 / 1（极限） | 20B | 102ms | 39.1Hz | 9.8Hz | 85%（不推荐常态） |

> 若 m = n = 4：轮长 ≈165ms，上行只有 ≈24Hz，且下行 4 帧占空很高——一般没必要，m 取 1–2 足够。

**四个必须先解决的点**：
1. **飞控不能用 8ms 轮询**：帧末到发车只有 3–5ms guard，必须用 IDLE/DMA 完成中断做"帧末事件"，否则 guard 要放到 10ms 以上、轮长被拉长。
2. **遥控器用 AUX 定拍**：每帧等 AUX 高 + guard 再发下一帧（`UAUX=1` 时 AUX 跟射频忙），不要用固定延时，避免漂移。
3. **收↔发切换时间**：guard 是否 3ms 够，要示波器实测（手册只给模式切换 9–11ms，没给收发切换）。
4. **轮长可变**：丢帧/超时会让某一轮变长（控制节拍短时降到 ~20Hz），验收要写"名义轮长 / 最大轮长"，不能假设恒 33.3Hz。

**结论**：可行，且比现网更抗丢帧；复杂度主要从"相位/窗口状态机"转移到"轮次/超时/探测状态机"，总量下降。建议作为主方案候选，与自由竞争 LBT 并行做台架对比。
