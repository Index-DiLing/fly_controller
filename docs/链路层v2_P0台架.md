# 链路层 v2 · P0 台架（FC bench + RC bench）

> 对应：协议规格 §11、实施计划书 §5（P0 标定）。**目标只有一个**：把 `F(n)`、真实空速、AUX 时序、
> 收↔发切换、UART 帧末延迟测出来，回填常量头（`LinkAirtimeBaseUs` / `LinkAirtimePerByteUs` /
> `LinkGuardUs`）。**测量期间不接电机，拆桨。**

两端都是**独立的 bench main**，不碰主线：

## 2. 烧录

1. **先烧一次主线固件**（任一历史版本即可，只为把 E220 的配置写进模块 flash：
   62.5k / 57600 / CH23 / 32B 分包 / UAUX=1 / URXT=3）。全新模块跳过这一步会出现
   "bench 一切正常但收不到"。
2. 飞控：烧 `build/bench/dl_fly_bench.hex`（ST-LINK Utility / STM32CubeProgrammer / pyocd 均可）。
3. 遥控器：`idf.py -p COMx flash`（**这一次**插 USB；烧完拔掉 USB，用外部 3.3V 供电）。
4. 两端上电，飞控的 USB-TTL 终端应出现：

```
=== DLX link bench (P0) ===
[cfg] USART1 PA9/PA10 115200 8N1 (bench-only)
[cfg] USART3 PD8/PD9 57600 8N1  M0=PD3 M1=PD4 AUX=PA2 EXTI2 both
[cfg] frameMax=32B (module packet=32B) air=62.5k  bench never writes E220 config
[cfg] core=168000000Hz  cycPerUs=168  IDLE char=173us
[aux] now=HIGH(idle) edges=0 drop=0
[aux] EXTI2 armed (both edges)
type 'help'
ok>
```

**上电自检三件事**：`aux now` 必须是 HIGH；`EXTI2 armed`；输入 `aux` 后手动碰一下 AUX 线
（或让对端发一帧），`edges` 计数必须增长。三者有一条不满足就先查接线，别急着量时序。

## 4. 每个测量项的步骤

### 4.1 空速真伪（对应记录表第 1 行）

```text
rc MODE SILENT
sweep 3
```

读 `busyUs` 列的**斜率**。判据：

| 配置空速 | 理论边际（10bit/B） | `sweep` 拟合出的 us/B 应约等于 |
|---|---|---|
| 62.5 kbps | 0.128 ms/B | 128 |
| 38.4 kbps | 0.208 ms/B | 208 |
| 19.2 kbps | 0.417 ms/B | 417 |
| 9.6 kbps | 0.833 ms/B | 833 |

历史实测（2026-10-06，旧主线）：8B=16.5ms / 12B=18.2 / 20B=21.2 / 32B=25.4ms ⇒ 斜率 ≈ **0.38 ms/B**
（≈ 21 kbps！）。若本次复测仍是 0.35~0.45，说明**62.5k 名不副实**（模块实跑约 19.2k，或 AUX 窗口
含固定内部开销）。结论写进「空速真伪」栏，并据此重算时隙预算。

### 4.2 `F(n)`（对应记录表第 2 行）

同一份 `sweep` 输出末尾的 `[fit]` 行就是答案：

```
[fit] F(n)=13500.00us + 380.00us/B*n  (n>=8, 25 pts)
[fit] => LinkAirtimeBaseUs=13500 LinkAirtimePerByteUs=380 (取整)
```

- 拟合只用 n≥8 的点（n=1..7 的固定开销抖动大，会把斜率拉偏）；每档取 reps 次里的**最小值**
  （最小值最接近"无排队"的真实空口时间）。
- 若 `sweep` 中途出现 `(no window)`：AUX 没跟上（线/极性），先解决 4.5 的接线问题。

### 4.3 收↔发切换（对应记录表第 3 行）

```text
rc MODE RESPOND len=8 guard=0
echo 0 8
echo 1 8
echo 3 8
echo 5 8
```

`echo g` 的 `guardUs` 应 ≈ `g×1000`（偏差就是本端"收到 → 写串口"的软件延迟）；回发后
`busyUs` 是模块射频忙时长。**切换代价 = 收到帧末 → 能发下一帧**，用 `round` 更接近真实：

```text
rc MODE PATTERN len=8 gap=22
round 22 0 8
round 22 1 8
round 22 3 8
round 22 3 21
```

**先明确 `round` 测的是什么**（2026-10-18 修正口径，之前写错过）：

- 它测 **"4 个连续上行 burst（U0..U3）+ 1 个 D0"的周转**，**不是** v2 协议的 120ms 轮次
  （v2 是 n=4 + m=1、s=22ms 的 5 槽超帧）。命名沿用旧文档，别按 120ms 理解。
- **"ideal" 有两个值**：`4*s`（D0 不占掉下一帧上行）与 `5*s`（D0 的空中时间 > 一个槽，
  下一帧上行被推迟）。`round` 打印里两个都给出；`roundUs` 落在 4*s 或 5*s 附近都属正常，
  落在两者之间才说明节奏不稳。
- 实测背景：21B 的 D0 空中时间 ≈25ms > s=22ms，所以**必然**吃掉下一帧上行 ⇒ 实测
  `roundUs≈110000`（=5×22ms）是预期结果之一，不是"bench 算错轮"。
  ⇒ 真正该记的结论是：**"4 上行 + 1 个 21B 下行"塞不进 22ms 槽的节拍里**，要么缩短 D0，
  要么加槽长/把下行放慢（写进 `LinkGuardUs`/时隙预算结论）。
- `d0OffUs`（软件口径：D0 写起点 − U3 的 IDLE 戳）应 ≈ `guard_ms×1000` + 一小段。
  它恒等于 guard 只能证明**软件等待**生效，不证明物理上已经能发。
- `d0AuxUs`（物理口径，2026-10-18 新增）：D0 写起点 − **U3 射频忙结束（AUX 上升沿）**。
  这个才是"物理收↔发切换"——不含 IDLE 的 173.6µs 偏置、也不受软件 guard 影响。
  **判断 guard 够不够看它**：`d0AuxUs` 若为 0 或极小，说明 guard 设太小（U3 射频还没收完就写了）；
  guard=3ms 时它应在 1.5~3ms 量级（= guard − UART/IDLE 等固定量）。
- 自检行 `[round] end rounds=.. dlSent=.. bursts=.. bursts/round=.. txtSkip=..`（字段顺序固定）：
  正常 `4.00`；`5.00` 表示每轮多收了一个 burst（最常见就是 D0 吃掉一帧后，把下一轮的 U0 多计了
  一个间隔；也可能是 RX 队列积压）。见 §4.6。
  **`txtSkip`** = 被过滤掉的可打印 ASCII burst 数（遥控器 bench 每 5s 的 `#STAT` 心跳、`#ACK/#PONG`
  等）。它们**不参与** idx/轮次统计——否则会把"4 上行 + 1 下行"的节奏切开，让 `roundUs` 出现
  131/176ms 甚至 4.89s 的离群值（2026-10-18 实测根因）。测量载荷首字节是 `0xA0..`，不受影响。

### 4.4 UART 帧末延迟（对应记录表第 4 行）

```text
rc MODE PATTERN len=8 gap=22
rx 5
```

- `rx` 打印的 `t` 是 **IDLE 中断**时刻，`dt` 是相邻两段突发的间隔（≈22000µs ± 抖动）。
- **IDLE 戳 = 最后一个字节 + 1 个字符时间（@57600 = 173.6µs）+ ISR 延迟（1~2µs）**。
  这是硬件的固定偏置，不是软件抖动：同一台架里 `dt` 不受影响，绝对量要减 173.6µs 才是
  "最后一个字节离线的时刻"。
- 与 AUX 对照：`rx` 打印的 `aux=` 是段末时刻 AUX 的电平。正常一帧结束后 AUX 应已回高；
  若 `aux=0`（仍忙），说明模块还没发完 → 串口收完 ≠ 射频发完（这正是 UAUX=1 要区分的事）。

### 4.5 裂包（对应记录表第 5 行）

```text
rc MODE SILENT
tx 21 50 30
tx 32 50 30
tx 8  50 30
```

- 本 bench 的发送走 **DMA 连续写**（`txStart()` 一次 `reset(n)+start()`，中间无任何等待/查询），
  这正是新链路层要求的方式（协议 §9.1）。
- 判据：每帧 `busyUs` 应是**单个** AUX 低电平窗口。若某帧出现两个窗口/`busyUs` 翻倍，
  说明模块把它拆成了两个射频包（URXT=3 字节时间被中间的串口空隙触发）。
- 若 `tx 21` 全部正常而 `tx 32` 偶发异常：检查是否是 UART 缓冲（512B TX ring）被打满。
- 对照实验：把 `sweep` 的连续性打破（例如在同一帧中途打印）不应出现——bench 已经禁止这样做。

### 4.6 22ms 抖动（对应记录表第 6 行）

```text
rc MODE PATTERN len=8 gap=22
round 22 3 21        # 连跑 5 分钟，期间别打印
stat
```

- `roundUs`：n（400 样本上限）、min/avg/max/**p99**。判据随口径：
  - 若 `bursts/round≈4.00`：avg ≈ 88000µs；
  - 若 `bursts/round≈5.00`（D0 吃掉下一帧，见 §4.3）：avg ≈ 110000µs；
  - 两者都要求 **p99 ≤ 125000**、max ≤ 140000（验收 §6.2）。
- `d0AuxUs`：物理收↔发切换，p99 应 ≤ `guard+2000`（guard=3ms 时约 ≤5000）。
  `d0OffUs`（软件口径）只用来确认 guard 被遵守（应 ≈ guard±1ms，P99 ≤10ms）。
- **`rxDrop` 必须为 0**（RX 队列被主循环打印挤掉就是测量作废）。
- **`txtSkip` 只作记录、不作判据**（2026-10-18 新增）：它是被过滤掉的可打印 ASCII burst
  （遥控器 bench 每 5s 的 `#STAT` 心跳、`#ACK/#PONG`）。5 分钟约 60 个属正常（心跳 5s + 命令应答）；
  数它只是为了证明过滤生效。**它不再进入 roundUs/bursts**——旧固件里这些心跳被当成上行帧，
  导致 `roundUs` 出现 131/176ms 与 4.89s 的离群值。
- **`auxDrop` 在 `round`/`rx`/`echo` 下不再是判据**（2026-10-18 修正）：
  `auxDrop` 计数的是**AUX 边沿环形缓冲**（128 深）溢出，与"链路丢帧"无关。
  旧固件在 round 里不消费边沿，5 分钟能溢出 24512 次——那只是没人读环，不是链路问题。
  现在每个循环都调用 `drainAuxEdges()` 消费边沿，因此正常情况下它也应为 0；
  但**只要它非 0 也不代表丢帧**，判据只看 `rxDrop`。`round` 结束会打印两个 drop 的增量。
- 遥控器侧抖动要从 `#STAT` 行读：`jmin/javg/jmax/jp99`（PATTERN 定拍偏差）。取回方式：

  ```text
  rc STAT
  rx 2
  ```

### 4.7 U3 抖动（对应记录表第 7 行）

同一段 `round 22 3 21` 里：

- `d0OffUs` 的 **max − min** = "U3 到达抖动 + 软件等待抖动"（IDLE 口径）；
- `d0AuxUs` 的 **max − min** = "U3 射频结束 → D0 写起点"的物理抖动（更接近链路层要补的余量）。

若差异 > `guard_ms`，说明 3ms guard 不足，或 U3 的 IDLE 戳被线程/打印拉偏（本 bench 在 IDLE
**中断**里打戳，没有旧主线 8ms 线程轮询的量化误差；若这里仍很大，先查是不是边测边打印）。

**`stat` 的读法（2026-10-18 修正）**：某个统计 **n=0 时打印 `--`**（无样本），不再打印 `min=0`
——旧固件里 `minV` 的初值是 0，会把"还没测过"显示成"最小值就是 0"。现在：

- `n=0 (--)` ⇒ 这一项还没产生样本（例如没跑过 `round` 就没有 `roundUs`）；
- `n>0` 的 min/avg/max/p99 才是测量值；`min=0` 现在是一个**真实的 0µs**，只在确实测到 0 时出现
  （例如 `d0AuxUs` 在 guard 太小时可能真为 0）。

## 6. 已知不确定点（必须在报告里回报 owner）

1. **AUX 极性**：按驱动合同「高=空闲、低=忙」（`DL_LIB/E220/dlx_e220_config.h:243-244`，
   手册 §5.2.4）。如果实测**相反**（空闲为低），`sweep` 会全部 `(no window)`；此时先 `aux` 看
   电平再决定是否改 `EXTITrigger`/极性假设。**不要**为了让测量"看起来通"而反接。
2. **EXTI 边沿**：bench 用双边沿（`EXTITrigger::Both`）。若 PA2 上有毛刺，`edges` 计数会远大于
   实际收发次数；此时把 `auxDrop()` 后紧邻的边沿配对逻辑当"抖动"看，先查硬件（上行串阻/去抖）。
3. **M0/M1 外部下拉**：`flight_config_gen.hpp:496-501` 要求模块侧 10k 下拉。若板上没有，
   MCU 复位期间模块可能停在模式 3（配置模式），表现为"bench 起来后一帧都收不到"。
4. **USART1 波特率**：bench 固定 115200，与主线 2Mbaud 不同。这是台架决定，**不是**生产配置；
   若 owner 的 USB-TTL 只支持固定档位，改 `test/bench/link_bench_main.cpp` 顶部的
   `kConsoleBaud` 一处即可。
5. **IDLE 偏置**：见 4.4。别把 `rx` 的 `t` 直接当"最后一字节到达时刻"用于协议窗口计算。
6. **功率档**：模块 flash 里可能是 T30S 的 30dBm 档（`E220_POWER_CODE=0`）。**桌上近距离对测**
   可能把接收前端压饱和 → 表现为"偶发 CRC 错/丢帧"。台架建议 1m 以上、或临时把一头挪远。
   bench 不写功率寄存器（那是配置），所以这一点只能靠距离/衰减器控制。
7. **构建环境（已实测）**：在受限会话里 `build/` 被 Windows 完整性标签挡住（不是文件内容问题，
   是沙箱的低完整性令牌写不了没有低完整性标签的目录；`build/` 由 EIDE 在非沙箱环境创建，因而没有）。
   构建脚本会自动检测并退到 `test/bench/_out/`（镜像完全相同，只是目录不同），并打印
   `with full access run: ... -OutDir "…\build\bench"`。用完全权限的会话重跑即可得到
   `build/bench/`。遥控器侧的 `idf.py` 另有一层限制：它用 Python asyncio 建命名管道捕获子进程输出，
   受限会话会报 `WinError 5`；**这不是工程问题**，在 RC 仓库（完全权限）里 `idf.py build` 已通过。

## 10. 2026-10-18 自动化复测结果（run_p0.py，COM11）

飞控 bench `[ver] p0 bench r3 2026-10-18`；遥控器 bench 新固件（PATTERN 带 dur 自停）。
原始数据：`test-data/p0_auto_20261018_122307.{log,summary.md}`。

| 项 | 实测 | 判据 |
|---|---|---|
| F(n) | **13555.36 + 387.27·n** us（F(8)=16553/F(32)=25948 同旧值） | PASS（13555±200 / 387±5） |
| tx 8/21/32B ×50 @20ms | 全部 `ok=50 miss=0` | PASS（无裂包） |
| round guard=0 / 1 / 3ms，8B DL | rounds 54/54/55，dlSent 54/55/55，bursts/round 4.02/4.07/4.02，rxDrop+0 | PASS |
| round 21B soak（60s） | rounds=546，dlSent=546，bursts/round=**4.00**，rxDrop+0 | PASS |
| `d0OffUs`（D0 − U3 IDLE） | min 2 / avg 2320 / max 3000 / p99 3000 | 软件 guard 正确 |
| `d0AuxUs`（D0 − U3 AUX↑） | min 178 / avg 2498 / max 3182 / p99 3181 | guard 3ms 时 D0 在 AUX↑ 后 ~3.18ms 发出 |
| `roundUs`（U0→U0） | n=400 min 106867 / avg 110497 / p99 113911 / max 176829 | bench 口径：21B D0 吃一帧 → 5×22ms；max 为 PATTERN 自停/漏帧边界 |
| `dlBusyUs` | 16508（8B）…21730（21B） | 与 F(n) 一致 |

**判读**
1. `F(n)`/裂包/定拍复测通过，常量头冻结值有效。
2. AUX 上升沿实际在"整帧 UART 排空之后"（d0Aux ≈ guard + 处理延迟，guard=0 时 178us），不是射频结束点；
   按 v2 的 `airEnd + guard` 发送，8B U3 时 D0 实际落在 AUX↑ 之后约 **1.4ms**（3ms − 1.57ms 排空），再叠 21B 发射 21.7ms，
   RC 收完 ≤114.4ms（117ms 窗口），guard=3ms 有约 1.4ms 物理余量 —— **3ms 保留，不再压缩**。
3. 21B D0 在 8B PATTERN 节拍下必然吃掉一帧上行（`bursts/round=4.00`、轮长 110ms）——这是 bench 测法，不是协议问题。
4. 旧版 `#STAT` 文本在串口上每行只打前 8 字节 hex，脚本无法完整还原；遥控器定拍用 4.4 原始数据（21976±20us）即可。
5. FC bench 的 `rc` 命令一次连续写 ≤32B，文本超过 30 字符会 `[rc] FAILED`；脚本已改用 `MODE PATTERN dur=ms`（默认 len/gap）。
