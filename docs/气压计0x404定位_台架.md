## 0. 一句话结论

`0x404` 是 `ExceptionCode::BARO_READ_FAILED`（`DL_LIB/dlx_exception.h:59`），但它**不等于"气压计寄存器读取失败"**：
全仓库共 **6 处**赋值，归为 4 类；**运行期真正可达的只有 2 条**——I2C 事务超时（`failStreak` 涨）与
"事务成功但补偿结果非法"（`failStreak` 不涨），两者共用同一个错误码，**必须靠旁证分开**。

I2C 侧目前最可疑的不是"读不到"，而是两件事：
1. 一次总线毛刺会让 `waitEvent` **空转 30~55ms**（离线反汇编推算，硬下界 ≈12ms）——而 `sns_baro` 的优先级(22)
   高于 `link_tel`(24)/`logger`(26)，这段空转会把它们**饿死**；
2. 错误路径**从不读/清 I2C 的 `AF/BERR/ARLO` 标志**，`recover()` 也只切 PE、不重跑 `I2C_Init`。

外加一条观察口径上的坑：现场日志里"0x404 与 0x204 同窗"只在 **一份**日志里成立（富集 6.4×），
另几份要嘛 base rate 饱和、要嘛没有功效——**不能拿"旁边没有 0x204"反推"与链路无关"**（§1.1）。

> 本文档给的是**假设 + 可执行的判别方案**，不是结论。哪些是代码事实、哪些是现场证据、哪些仍需上板，
> 每一处都标了；台架跑完把结果填进 §8，再回来把假设降级成事实。

三条关键结论（都直接影响怎么定位）：

1. **"同窗"只在其中一份日志里是真的耦合。** 直接报"同窗率"会被 0x204 自身的密度顶满：
   22:43 那份看着 100%，但零假设期望就有 15.3 次 ⇒ 富集 0.4×，**等于随机**。
   反过来 22:28 那份是 20 次 vs 期望 3.1 次（**6.4×**，泊松 p<1e-4）——这是唯一有判别力的日志。
   其余几份 0x204 稀疏到期望 <1 次，**没有功效**（不是"阴性结论"）。
   ⇒ 不能拿"旁边没有 0x204"当"与链路无关"的证据。
   （共同复核见 [`test-data/baro_bench/verification.md`](../test-data/baro_bench/verification.md) §7。）
2. **不能再用"Δt 都是 0.000s"来证明"同一次停顿"。** 全 9 份日志里相邻两行落在同一毫秒的比例有
   **54%**（上位机按收到时刻打戳 + 飞控日志线程按 5ms 节拍排空队列，
   `flight_config_gen.hpp:219`）⇒ 0.000s 是批处理底噪。可用的证据只有第 1 条的富集。
3. **控制环没有被拖慢（尾部检查）。** 全部 9 份日志里 `[Perf] 主循环 最大` **没有一个样本 >5000µs**
   （极值 1216~1266µs）——要找 ~40ms 的尖峰有 30× 以上余量。
   这与 §3.3 的优先级链**一致**（卡的是 prio>22 的 `link_tel`/`logger`，不是 prio 10 的控制环），
   但**它判不了 H1**：控制环本来就比 `sns_baro` 优先级高，只排除"全局/prio≤10 停顿"；
   唯一能推翻它的反例是控制环与气压计线程之间存在阻塞依赖（锁/阻塞信箱）——日志既没有反例也没有证明没有。
4. **这些日志无法用来判断"失败是不是成簇"。** `app_sensors.hpp:552` 只在健康边沿上报
   （`app_health.cpp:55-62`），连续失败只会留下第一条；两次成功之间（ODR=50Hz ⇒ 每 20ms 一个真样本）
   的失败全部被折叠。（同理，日志里 0x404 的"间隔直方图"测的不是失败间隔，而是**失败事件**间隔。）
   **更关键**：`0x0204` 本身也不配当"链路被扰动"的标记——它只在轮次进 ACQUIRE 且走健康边沿限流时上报一次
   （`app/link/app_link_thread.hpp:900-906`），一次 40ms 空转造成的单帧 TooSoon/OffGrid **不会**产生 0x204。
   ⇒ **必须由台架自己数原始失败次数**，这也是本台架存在的理由之一。

## 2. `0x404` 的来源：6 处 raise 点，运行期只有 2 条 [代码事实]

verifier 全量清点过：`BARO_READ_FAILED` 在仓库里共 **6 处**赋值。按"能不能在运行期（飞行中）发生"分列如下——
**结论是运行期只有 A、B 两条**，这直接决定了假设空间的大小：

| 类 | 位置 | 触发条件 | 运行期可达？ | 与 I2C 事务的关系 | 可观测判别 |
|---|---|---|---|---|---|
| **A** | `DL_LIB/BMP388/dlx_bmp388.hpp:328-333` | `readRegs(0x03,7B)` 事件超时 | **是**（每次 `read()`） | **是**（事务失败） | `failStreak++`、`staleStreak++`、`IICBus::eventTimeouts()` 有增量 |
| **B** | `DL_LIB/BMP388/dlx_bmp388.hpp:513-515` | 突发读**成功**，但补偿结果非有限或 `pressure <= 0` | **是**（每次 `read()`） | **否**（数据已读到，是字节/系数不可信） | `failStreak`/`eventTimeouts` **都不变** |
| C1 | `DL_LIB/BMP388/dlx_bmp388.hpp:220-226`（`readCalib`） | 21 字节标定块读超时 | 否（仅 `tryInit()`） | 是 | 只在开机 `init`，带 `stage=calib` |
| C2 | `DL_LIB/BMP388/dlx_bmp388.hpp:466-474` | init 阶段回读配置超时 | 否（仅 `tryInit()`） | 是 | 只在开机 `init`，带 `stage=readback` |
| D | `app/sensors/app_sensors.hpp:545-547` | `baroReference.apply()` 返回 false（高度非有限）→ **硬编码**报 `BARO_READ_FAILED` | **当前驱动下不可达**（见下） | **完全无关** | 这条路径上 `baro.read()` 返回的是 `NewData` |

> **D 为什么不可达（仍然保留、但别把它算进假设空间）**：`BaroReference::apply()` 唯一的 false 分支是
> `!std::isfinite(sample.altitudeM)`（`app/sensors/app_measurement_reference.hpp:36`），而 `altitudeM` 来自
> `getAltitude(pressurePa)`；驱动在 `:513` 已经保证 `pressurePa` 有限且 `>0`，此时
> `44330·(1 − (p/101325)^0.190295)` 恒有限。所以它是**防御性代码**，不是运行期来源。
> 但它确实和"读寄存器失败"共用同一个错误码 —— 只按错误码检索代码的人会把它误当成一条真实通路。

`read()` 的失败语义再提醒一次（`dlx_bmp388.hpp:495-520`）：

```cpp
const ReadResult result = readRaw(rawPressure, rawTemp, err);   // A 在这里产生 err
if (result != ReadResult::NewData) return result;
...
if (!std::isfinite(temperature) || !std::isfinite(pressure) || pressure <= 0.0f) {
    err = ExceptionCode::BARO_READ_FAILED;                      // B 在这里覆盖 err
    return ReadResult::Failed;
}
```

⇒ **`err == 0x404` 无法区分 A 和 B**。判别只能靠旁证：`failStreak` / `eventTimeouts()` 的增量、以及
失败瞬间的 `SR1/SR2`。台架固件就是按这个判别的（`[fail] kind=tx|comp`）。

### 上报频率的语义 [代码事实]

`app_sensors.hpp:552-553` 只在 `healthClear(SensorHealth::BARO)` 为真时上报，而
`Health::failure()` 只在"可用→不可用"的**边沿**返回 true（`app/sensors/app_health.cpp:55-62`）。
所以：**每条 0x404 日志 = 一次"从健康跌到失败"的边沿**；连续失败只在第一条上报。
换句话说日志频率 ≈ 失败**事件**频率，不是失败次数频率——不会因为密集失败而刷屏，也就不会"看起来比实际轻"。

## 3. 机制链：为什么"读失败"会表现为"系统停顿" [代码事实 + 假设]

### 3.1 失败路径的阻塞时长不受控

`DL_LIB/dlx_iic.hpp:149-172`：

```cpp
static constexpr uint32_t kEventWaitLimit = 200000u;
bool waitEvent(uint32_t event) {
    for (uint32_t i = 0; i < kEventWaitLimit; ++i) {
        if (I2C_CheckEvent(getI2C_TypeDef(), event) == SUCCESS) return true;
    }
    busError = true;  _lastFailedEvent = event;  ++_eventTimeouts;  return false;
}
```

- 这是**轮询次数上限，不是时间上限**。用仓库里已有的编译产物（`build/FLY/.obj/release.o` +
  `stm32f4xx_i2c.o`，`-O3`/Cortex-M4/168MHz）反汇编数出来：循环体 9~13 条指令（profile switch 与事件掩码
  **每轮重做**——因为 `I2C_CheckEvent` 是独立 `BL`，编译器无法证明它不改 profile）+ `I2C_CheckEvent`
  慢路径 11 条指令 + 两次 I2C1 寄存器读（APB1=42MHz 的桥同步开销）+ 调用/分支开销。
  完整推导、反汇编片段与复现命令见
  [`test-data/lead_offline/measurements.md`](../test-data/lead_offline/measurements.md)，
  独立复核见 [`verification.md`](../test-data/baro_bench/verification.md) §7。
  复核后的修正与结论：
  - **`read()` 里 `waitEvent` 被内联了 3 处**（第一处用 `r7=200000`，第二处用 `r4`，第三处 `r9`），
    上面引的是第一处，三处的循环结构相同。
  - `I2C_CheckEvent` 有**快路径**（SR1 只有 TxE 时只读一次 SR1 就返回），所以单轮耗时**不是常数**；
    `AF` 置位时一定走慢路径，但"每次超时耗时固定"这个说法不成立。
  - 因此 **30~55ms 只能当量级（±50%）**，权威值由台架 `[fail] durUs` 给出。
  - 硬下界是可靠的：200000 轮 × ≥10 周期 ÷ 168MHz ≈ **12ms** ⇒ "tx 类失败是 µs 级"可以先验排除。
- 一次失败的 `read()` 只花**一次**这样的空转：`waitEvent` 一超时就置 `busError`，同事务后续步骤
  （`start/sendAddress/sendByte/receiveByte` 开头的 `if (busError) return;`）全部短路，`stop()` 不等待。
  ⇒ **每次 tx 类 0x404 都会让 `sns_baro` 线程独占 CPU 约 30~55ms**（对比：`recover()` 的 9 个脉冲 ≈ 90µs）。
- 空转期间**没有任何错误标志检查**：`AF`/`BERR`/`ARLO`/`OVR` 一个都不看（见 3.2）。
- **已上板实测（2026-10-18，见 §8.2）**：单次超时 ≈ **64ms**（`inject` 每次迭代 11 次事务耗时 0.700s 反算），
  与这里的离线估算同量级、略偏高。**实际观察到的 `[fail] durUs` 会直接给出这个值**（健康事务在 400k 下只有 227µs）。

### 3.2 错误标志从来不清 [代码事实]

全仓库 grep `I2C_ClearFlag | I2C_GetLastEvent | I2C_FLAG_AF | ARLO`：**0 命中**。

一次 NACK 会让 `SR1.AF` 置位。按 RM0090 的 I2C 章节，`AF` 必须由软件写 0 清除，否则主机无法继续产生
START/继续传输 —— **[假设：这条硬件行为需台架 `inject` 实验确认，见 §5]**。当前代码里：

- `waitEvent()` 超时后只置 `busError`，**不清 AF**；
- `IICDevice::read()`（`dlx_iic.hpp:350-372`）只在**下一次**事务开始时才 `if (bus.hasError()) bus.recover();`；
- `recover()`（`dlx_iic.hpp:277-306`）做的是：PE 关 → 手工 9 个 SCL 脉冲 + STOP → 引脚回 AF4 → PE 开 →
  `busError=false`。**它不重跑 `I2C_Init`，也不显式清任何 SR1 标志。**
  （PE 关/开是否会顺带清掉 AF，属于"芯片行为，别靠记忆"，正好是 `inject` 要回答的问题。）

⇒ 如果一次毛刺把 `AF` 粘住且 `recover()` 修不好，后续每次调用都会以超时收场；如果 `recover()` 能修好，
失败就是孤立的单次。**这两种世界在日志里长得一样，但在台架上是两个不同的 `attempts_to_ok` 分布。**

### 3.3 线程优先级：为什么停顿会打到链路线程 [代码事实]

| 线程 | 优先级（RT-Thread，数字越小越高） | 依据 |
|---|---|---|
| main / 控制环 `stack.run()` | **10** | `rt-thread/src/components.c:28`（`RT_THREAD_PRIORITY_MAX/3`，MAX=32）、`release.cpp:63,162` |
| `sns_imu` | 21 | `app/runtime/app_runtime_limits.hpp:22` |
| `sns_baro` / `sns_rng` / `sns_flow` / `sns_gnss` | **22** | `app_runtime_limits.hpp:23`、`app_sensors.hpp:472-489` |
| `link_tel` | **24** | `app/control/app_flight_stack.hpp:700` |
| `logger` | 26 | `app_flight_stack.hpp:715` |

气压计线程（22）一旦在 `waitEvent` 里空转约 40ms，**优先级低于它的 `link_tel`(24) 与 `logger`(26) 在这段时间内
一步都跑不了**（RT-Thread 抢占式调度里低优先级线程无法抢占高优先级线程）；而控制环(10)与 IMU(21)不受影响。

⇒ **一条机制可以同时解释两个症状**：气压计 I2C 毛刺 → `waitEvent` 空转 ≈ 40ms（离线反汇编推算 30~55ms）
→ 链路线程被饿死同一段时间 → 链路侧报 TooSoon/OffGrid/0x0204；同一时刻气压计报 0x404。
两者不是"共同原因", 而是**同一个原因的上下游**。

> **"δ∈(6,18)ms 比 40ms 小"这件事，复核后降级为「未测量项」，不再是矛盾**：
> `δ` 是链路侧判据**推论**出来的量（审计 `:72`），而链路的 `onSlotGrid` 用的是"**最近网格点**"判据
> （容差 `slotUs/4`，`DL_LIB/link/dlx_link_sched.hpp:155,547-559`）——40ms 的延迟在 24ms 的槽上会被折成
> 8ms 量级的残差。两者**量的不是同一个东西**，所以不能互相证伪。
> 台架 `[fail] durUs` 能回答"本 MCU 上一次超时到底多久"，但**收不了现场的尾**：要收口还需要审计
> §210-215 的 Phase 0 观测（0x404 边沿带 ms 时间戳 + 该次 `read()` 耗时 + `rt_sem_take` 偏差，同一时基）。
> 推导与不确定性见 [`measurements.md`](../test-data/lead_offline/measurements.md) §4。

## 4. 假设清单与判别方法

| ID | 假设 | 支持它的代码事实 | 台架/测试判别 | 若成立的修法 |
|---|---|---|---|---|
| **H1** | 一次 NACK/总线错误把 `SR1.AF` 粘住，`waitEvent` 空转到上限 → 单次毛刺放大成**连续失败** | §3.2 全仓库无清标志；`recover()` 只切 PE | `inject`：`attempts_to_ok` 分布；`[fail] sr1` 的 `af` 位；失败聚类长度直方图；`test/iic_error_recovery_test.cpp` | 超时/恢复路径显式清 `AF/BERR/ARLO/OVR`，`recover()` 重跑 `I2C_Init` |
| **H2** | 400kHz 下信号完整性/上拉不足 → 偶发位错 → NACK/BERR | `cfg::hw::baro::kSpeed = 400000`（`flight_config_gen.hpp:342`）；400k 是 BME280 时代沿用的值（:343 注释） | `speed 100000` vs `400000` 的失败率对比；`bus` 看 SCL/SDA 空闲电平 | 降速/加/减上拉；改配置即可 |
| **H3** | 观察到的 0x404 里有一部分根本不是 I2C 失败 | §2 的 B / D 两个来源 | 台架 `kind=tx|comp` 比例；`test/bmp388_error_provenance_test.cpp` | 拆错误码（B 用独立码；D 不该报 0x404） |
| **H4** | 总线被从机拉住（SDA 常低）→ `recover()` 的 9 个脉冲是否真能救回来 | `dlx_iic.hpp:277-306` 是唯一恢复手段 | `bus` 的 scl/sda 电平；`recover` 的 `next_ok` | 恢复流程改 `I2C_DeInit`+`I2C_Init`；必要时加从机复位 |
| **H5** | 失败与"短系统停顿"同窗（不只是链路，任何长 ISR/关中断也会） | 现场 δ∈(6,18)ms；`kEventWaitLimit` 是次数上限 | `[fail] gapUs/durUs` 分布；`irqblock` 复现实验 | 把等待改成时间上限 + 提前检测错误标志（把空转从几十 ms 压到 µs 级） |
| **H6** | 失败率与负载/供电相关（SPI/DShot/电流噪声） | 400k + 长线 + 动力系统共地 | `stress on` 前后失败率对比；失败行带 ADC 电压 | 硬件/布线；软件上降速与加重试 |
| **H7** | **事务传输途中被打断**（长 ISR / 抢占）⇒ I2C 硬件 OVR，突发读"成功"但字节错位/丢失 ⇒ 落到 B 类（comp），**不产生空转** | `dlx_iic.hpp:240-249` 每字节只在 `I2C_EVENT_MASTER_BYTE_RECEIVED` 上等一次；400kHz 下一个字节只有 22.5µs，软件晚读 DR 就是 OVR | `[fail] kind=comp` 且 `durUs` 是**正常量级**（几百 µs 而不是几十 ms）；`raw` 6 字节自身矛盾（例如压力高位被顶掉） | 接收改成 DMA/中断；或把每个事务的临界区保护起来（`InterruptLock`） |

优先级建议：**先判 H1/H3**（两者都能靠本台架 + 主机测试直接判定，且修法明确），再判 H7（用 `kind=comp` 的
`durUs` 与 `raw` 指纹判）、H2/H6（需要重复实验），H4/H5 是 H1 的补充证据。

> H7 与 H1 的区别很关键，因为修法完全不同：H1 是"失败后不收尾"，H7 是"传输中途被抢走 CPU"。
> **注意判别力的边界**：不能用"真机日志里多数 0x404 旁边没有 0x204"来预判 H7——`0x0204` 本身极稀疏
> 且被健康边沿限流（§1.1 结论 4），那几份日志对此**没有功效**。H7 的判据只有台架自己给的
> `kind=comp` + 正常 `durUs` + `sr1` 的 OVR 位（0x0800）+ `raw` 字节指纹。

台架固件的命令契约（Python 解析器按它写；13 条冻结格式串由 bench-fw 从**链接后的 .bin** 里逐字核对过）：

```
ver | help | cfg | sr | bus
init [hz]                  # 每次尝试打一行 [init] stage=... result=...；上电另打一行 [boot] baro init=<OK|FAIL>
soak <ms> [period_ms]      # 持续读, 每秒一行 [soak], 结束一行 [soak.end]；器件未初始化时拒绝执行并打 [err] not-initialized
inject <n>                 # 对 I2C1 上不存在的地址 0x33 发一次写 => 必然 NACK => 再看恢复要几次
speed <hz>                 # 重配 I2C1 速率并重新 init 器件
stress <on|off>            # SPI1 BMI088 读 + I2C2 VL53L1X 探测 + ADC, 模拟飞行并发负载
irqblock <us> <period_ms> <on|off>   # TIM7 更新中断里忙等; period_ms ≤ 65(16 位 ARR 上限), 且要求 us < period_ms*1000
recover | stat | reset
```

失败行（每次失败一行，可直接进 CSV）：

```
[fail] i=<序号> t=<ms> kind=<tx|comp|other> sr1=0x.... sr2=0x.... lastEv=0x........ evD=<增量> \
       status=0x.. raw=<6 字节> durUs=<本次事务耗时> gapUs=<距上次尝试> streak=<连续失败数> [err=0x....] [scl=0 sda=1]
```

（`err=` 与 `scl/sda` 是 r2 起的增量：`err=` 只在 `kind=other` 时参与判读；`scl/sda` 是**失败当刻** PB6/PB7 的电平，
取自 `baro_bench_main.cpp:405-408` 那个"`read()` 返回后、任何 recover 之前"的快照块，与 `sr1/sr2` 同源。
它给 H4 提供了自动化判据：失败行**反复**出现 `scl=0` 或 `sda=0` ⇒ 总线可能被从机拉住；单次出现不足以定性。）

`kind` 的判定**不是猜的，而且带错误码门禁**：只有 `err == BARO_READ_FAILED(0x0404)` 才进二选一——
`eventTimeouts()` 有增量或 `baro.failCount()>0` ⇒ `tx`（来源 A）；`failCount()==0` ⇒ `comp`（来源 B）。
其它错误码（`0x0403 CALIB_INVALID`、`0x0401 NOT_FOUND`…）一律记 `kind=other`，**不混进 tx/comp 统计**；
不变量 `fail == tx + comp + other`。summary 里的 `other* = fail − tx − comp` 是**推算列**
（`[soak.end]` 契约里没有 `other` 字段），逐行比例仍以实际捕获到的 `[fail]` 行为准。

> 这条门禁是 verifier 在集成预审里逼出来的，代价很值：台架开机不初始化器件时，`read()` 会直接返回
> `0x0403`，若没有门禁就会把**未初始化**误报成 `comp`，而 `comp` 恰好等于"与 I2C 无关"这个结论 ——
> 一场"健康板子得出反向结论"的假阳性。现在未初始化会同时在校验层(`[err] not-initialized`)与
> 解析层(`comp==att` 且 `maxdurUs<=1` ⇒ 该段结论作废)被拦下，而且默认流程里补了 `init` 步骤。

`inject` 的判据口径也要写清（别把相关当因果）：
- `attempts_to_ok == 1`：**两种情形不可分**——(a) `recover()` 的 PE 关开真的清掉了 AF；(b) AF 根本没挡住事务。
- `attempts_to_ok > 1`：与"AF 未清"相容，但**同样兼容 H4**（从机拉住 SDA / 信号余量不足 / 器件自己卡住）。
- `attempts_to_ok == -1`（上限内从未恢复）：**AF 粘连的最强证据**，单独判读。
- 要区分 (a)/(b)，看 `[recover] sr1_before/sr1_after` 是否真带着 `AF`(bit10=0x0400)——所以流程里在
  `inject` 之后**立刻**补了一次 `recover`（`recover@post-inject`），而不是等收尾那次（那时 SR1 多半已经干净）。

## 6. 操作步骤（需要接线与烧录）

前置：ST-LINK/J-Link + USB-TTL。USART1 = PA9/PA10 接 USB-TTL 的 RX/TX（台架固定 115200 8N1，**不是**主线的 2Mbaud）。

1. 构建：`powershell -ExecutionPolicy Bypass -File .\tools\bench\build_baro_bench.ps1 -Rebuild`
   （产物 `build/bench_baro/dl_fly_baro_bench.hex`；若该目录不可写会自动退到 `test\bench\_out_baro\`）。
2. 烧录 bench 镜像（它会替换 release.cpp 的 `main`，**不要**在装机前飞这个镜像）。
3. 先做**静态**实验（桨叶拆掉，电机不上电）：
   `python tools\bench\run_baro.py --port COMx --soak 60000 --inject 20`
   它按顺序跑：版本核对 → `cfg/sr/bus` → `reset` → **`init`** → 400k 基线 soak → 注入 → **`recover@post-inject`**
   → 100k soak → 400k soak → 带负载 soak → `recover` → `stat`。
   **`init` 这一步不能省**：器件没初始化时 `read()` 直接返回 `0x0403`，脚本会把整段标成"数据不可信"并以
   退出码 4 结束（0 正常 / 1 步骤失败 / 2 串口环境 / 3 版本门禁 / 4 器件未初始化）。
4. 若基线 soak 零失败，再加长到 10~30min 复跑；若基线有失败，按 §7 判据表对号入座。
5. 需要"是否与动力/供电相关"时，再单独跑 `stress on` 长 soak（仍建议先拆桨）。

### 6.1 烧录命令（STM32CubeProgrammer CLI，2026-10-18 实机工具版本 2.21.0）

USB-TTL 接 USART1（飞控 PA9→TTL RX、PA10←TTL TX、GND 共地），终端设 115200 8N1。

## 7. 判据表（结果 → 结论）

| 观察 | 结论 | 下一步 |
|---|---|---|
| 基线 soak 报 `comp==att`、`tx=0`、`failrate≈1.0`，且 `maxdurUs≈0` | **不是结论，是器件没起来**（未初始化 ⇒ `0x0403` 被门禁挡成 `kind=other`，老固件会误记成 `comp`） | 先看 `[boot]`/`[init]` 与 `[err]`；脚本对此会警告并以退出码 4 结束 |
| `inject` 后 `attempts_to_ok` 分布里出现 >1，且失败行 `sr1` 的 `af=1` | **H1 成立**：NACK 粘住 `AF`，恢复要靠下一次事务的 `recover()`（或压根没恢复） | 上 §9 最小修复；改完用同一实验 A/B |
| `inject` 后总是 `attempts_to_ok=1`，但 soak 仍有 `kind=tx` 失败 | H1 不是主因；看失败行 `lastEv`（卡在哪个事件）与 `durUs` | 转 H2/H4/H5 |
| `kind=comp` 占失败的大头 | **H3 成立**：这些 0x404 与 I2C 事务无关 | 拆错误码 + 查数据/系数可信度 |
| `kind=comp` 且 `durUs` 是正常量级（几百 µs） | **H7 成立**：突发读其实完成了，是字节被顶掉/错位（OVR） | 查 `raw` 字节指纹；接收改 DMA/中断，或给事务加临界区 |
| `kind=tx` 且 `durUs` 落在 30~55ms | §3.1 的空转量级成立（H1/H5 的机制面） | 按 §9 改等待逻辑 + 清错误标志 |
| `100000` 的失败率远低于 `400000`（相同 soak 长度） | **H2 成立**：400kHz 余量不足 | 降速或改硬件；400k 这个值只是从 BME280 继承来的 |
| `stress on` 后失败率明显上升 | H6 成立（负载/供电/串扰相关） | 查供电与布线；软件上降速 + 重试 |
| 失败行 `durUs` 稳定在几十 µs（正常量级）而仍判失败 | 不是超时空转；可能是数据被污染（落在 B）或事件判据过严 | 查 `raw` 字节与 `lastEv` |
| 失败聚类长度普遍为 1，且失败后 `recover` 的 `next_ok=1` | 单次毛刺 + 恢复有效；但**每次仍是 30~55ms 量级的停顿** | 优先做 H5 的"把空转改成时间上限 + 早停" |
| **失败行的 `scl`/`sda` 反复出现 0**（summary 的"H4 总线被拉住"节占比高）且 `[recover]` 的 `next_ok=0` | 总线被拉住（H4）；配合 `sr2` 的 BUSY 位一起判 | 查从机/供电；恢复流程加固（§9-2） |
| 失败行的 `scl=1 sda=1`（总线空闲）却仍 tx 失败 | 不是被拉死；转 H1（标志/判据）或 H5（空转） | 看 `[fail] sr1` 的 AF 位与 `lastEv` |
| `irqblock` 回 `[err] bad-arg irqblock-clock` | 该配置下定时器计数时钟不是 1MHz 整数倍（本板不会出现）；实验拒跑而不是静默按截断值跑 | 换 `period_ms` 或修 RCC 配置 |

> 判据表是**排他**设计的：H1/H2/H3/H6 各自的"指纹"互不重叠，同一份日志应只落进一格。
> 若落进两格以上，说明台架有判别力缺陷，先修台架而不是下结论。

### 8.2 这次实测**证实**的结论

1. **H1 的机制面成立，而且比"放大"更严重——它是"永久性"的**（硬件实测，不是推断）：
   - 一次对幽灵地址 `0x33` 的写（必然 NACK）→ `pre_sr1=0x0000` 变 `post_sr1=0x0400`（**AF=1**）；
   - 之后**连正常地址 0x76 的读也全失败**（`next_ok=0`），10 次尝试内一次都没成功（`attempts_to_ok=-1`）；
   - 第 2 次注入时 `pre_sr1=0x0500` = **AF(0x0400) + BERR(0x0100)** —— 重试本身把 BERR 也置上了；
   - 驱动唯一的恢复手段 `recover()`：`sr1_before=0x0500` → **`sr1_after=0x0501`（AF/BERR 仍为 1）**、`sr2=0x0003`（MSL|BUSY）、`next_ok=0`
     ⇒ **`recover()` 的"PE 关/开 + 9 个 SCL 脉冲"清不掉 AF/BERR**；
   - 随后 `speed 100000`（内部重跑 `I2C_Init`）→ 总线**立刻**恢复正常：紧接着的 20s soak 0 失败、`evTimeouts` 不再增长
     ⇒ **只有 `I2C_Init` 能清**，而主线固件运行期**从不**重跑 I2C 初始化。
   - **对主线的含义**：一旦飞行中出现一次 NACK/总线错误，气压计会**永久失效直到重启**，并且每次重试都要空转（见下），
     等于让 `sns_baro` 长期占着 ~89% 的 CPU（8ms 睡 + ~64ms 空转），持续饿死 `link_tel`(24)/`logger`(26)。
2. **单次事件超时的阻塞时长 = ~64ms（实测）**：`inject` 每次迭代 = 1 次注入 + 10 次重试 = 11 次事务，
   时间戳显示每次迭代 **0.700s** ⇒ 单次 `waitEvent` 超时 ≈ **64ms**；`evTimeouts` 从 0 涨到 221 ≈ 20×11。
   这与 §3.1 的离线反汇编估算（30~55ms）同量级、略偏高——**§3.1 的机制与量级确认**，权威值改用 64ms。
3. **台架这条总线是干净的**：400kHz 与 100kHz 各跑 20s、再加"SPI+ I2C2 + ADC"负载，**16,653 次事务零失败**。
   ⇒ 在本台架（裸机、短线、无电机）上 **H2（400kHz 余量）与 H6（负载串扰）都未复现**；
   但这不能替飞机上的线束/动力环境开脱（台架没有 RT-Thread 抢占、没有 DShot/电机）。

### 8.3 这次实测**未能**回答的，以及新发现的台架缺陷

- **没能回答"现场那批 0x404 是 tx 还是 comp"**。反推：本次证明"AF/BERR 一旦置位就永久失效、且 `recover()` 救不回"，
  而现场日志里 0x404 是**反复出现、每次都能自愈**（48 次/421s，且 `[Link]`/`[Perf]` 节拍全程正常）——
  所以**现场那批不是"标志位粘连"型**，只可能是 ① `kind=comp`（事务其实成功、数据/补偿非法），
  或 ② **不置标志的 tx 超时**（一次 ~64ms 空转，之后 `recover()` 的 9 脉冲把状态机拉回来）。
  要分开这两者，**必须在主线固件里给 0x404 边沿加观测**（`err`+`failCount`+`eventTimeouts`+`SR1/SR2`+本次读耗时），
  现有日志没有健康行、也没有事务耗时，答不了。
- **台架缺陷（已修，r3）**：`soak` 的绝对计时原来用 32 位差值，**在 DWT 的 25.566s 回绕点归零**
  ⇒ `soak <ms>` 只要 ms > 25566 就永远不会自己结束（本次 60s soak 的 `t` 在 25s、51s 各复位一次，
  最后是被 `inject` 的字节中止才打出 `[soak.end] t=23876`；脚本把它判 FAIL 是正确的）。
  r3 改成逐轮累加（`uint64_t elapsedCyc`），verifier 已用算术仿真复核（旧写法 2000 万轮不 break、新写法 7500 轮精确 break）。
  ≤25s 的 soak 不受影响，且计数器是累计的，所以**上面 §8.1 的失败率数据依然有效**。
- 下一步的实验顺序建议：① 修好 soak 后跑 10~30min 长 soak（400k）；② 跑 `irqblock` 叠加 soak
  （那是台架**唯一能主动注入**的"H7：事务途中被抢"触发器，看是否出现 `kind=comp` + `sr1` 的 OVR 位 0x0800）；
  ③ 主线固件加 0x404 边沿观测后上飞机复现，把现场失败定性为 tx/comp。

## 9. 加固（**2026-10-18 已落地**，依据 §8.2 的实测证据）

原则仍然是"先测再改"：§8.2 已经把"一次 NACK ⇒ AF 粘住 ⇒ `recover()` 救不回 ⇒ 只有 `I2C_Init` 能清"
测成了事实（20/20 未恢复 + SR1 0x0500→0x0501），所以下面两条从"建议"变成了"已实施"。

### 9.1 改了什么

| # | 文件 | 改动 |
|---|---|---|
| 1 | `DL_LIB/dlx_iic.hpp` `waitEvent()` | 每 512 轮查一次 `SR1` 的 `AF/BERR/ARLO/OVR`（`i==0` 必查），**置位立即 `return false`**；不再空转 200000 轮（实测 64ms → 亚毫秒级）。**故意不清标志**：失败瞬间的 SR1 是台架/诊断最需要的证据，清标志统一交给下一次事务开头的 `recover()`。 |
| 2 | `DL_LIB/dlx_iic.hpp` `init()` / `recover()` | `init()` 保存 `I2C_InitTypeDef`；`recover()` 在"9 个 SCL 脉冲 + STOP + 引脚回 AF4"之后**重跑 `I2C_Init` + `I2C_ClearFlag(kErrorFlags)`** 再使能。 |
| 3 | `DL_LIB/dlx_iic.hpp` | 新 getter `errorLatches()`：因错误标志提前放弃的次数，与 `eventTimeouts()` 分开——前者=总线上真出过错标志，后者=事件迟迟不来。 |
| 4 | `app/sensors/app_sensors.hpp` `baroLoop()` | **第二道防线**：连续失败 ≥ `cfg::sensor::baro::kFailLimit`(=10) 时，在**气压计线程内**做 `baroBus.recover()` + `baro.tryInit()`，并 `logLine` 一行成功/失败与 `err`。健康/异常上报语义不变。 |

`kErrorFlags` 用的是设备头里的 `I2C_SR1_AF|BERR|ARLO|OVR`（数值与 SPL 的 `I2C_FLAG_*` 相同），这样同一份驱动在
**真机**和**主机侧寄存器级替身**（`test/iic_stub/`）两种编译环境里都成立。

### 9.2 为什么恢复**不**放在控制线程（回答"抛异常给控制线程再重启总线"这个方案）

方向对，但落点要改。控制线程确实会收到 0x404（`FaultChannel` → `RefreshHealth`），但把它当**恢复**入口有三个问题：

1. **只会有一次机会**：`healthClear()` 只在"可用→不可用"的**边沿**返回 true（`app_health.cpp:55-62`），
   连续失败不再上报 ⇒ 靠异常触发恢复，第二次失败就没人管了。
2. **跨线程抢总线**：总线有唯一使用者（`sns_baro`）。让控制线程（prio 10，能抢占）去 re-init 一个
   "另一个线程正卡在 `waitEvent` 里"的外设，属于在没有所有权的情况下改共享外设——即使能跑通也是竞态。
3. **恢复离故障点越远越慢**：空转的代价发生在传感器线程里；恢复动作应该就在那里、紧随失败。

所以最终分工是：**恢复留在总线所有者线程**（驱动自动清 + 传感器线程的连续失败兜底），
**控制线程只保留"降级决策"**（收到异常 → 刷新健康 → 决定不用气压计）。两者互不依赖。

### 9.3 验证状态与还需上板确认的一条

- 编译：`release.cpp` 按 `compile_commands` 重放编译 exit=0；bench 构建 `LINK OK`（镜像 hex 163,176→165,590，因为驱动新代码进镜像）。
- 主机测试：`iic_error_recovery_test` 从 `KNOWN-GAP` 翻成 **`FIXED`**（`recover()` 期间 `I2C_Init delta=1`、
  `I2C_ClearFlag delta=1`、下一次事务成功）；已改成**硬回归门**（再加一条"`I2C_CheckEvent` 调用次数 < 200"的
  不空转断言），谁把加固删掉，测试就红。
- **上板 A/B（还没做，需要你重烧一次）**：重烧后的 bench 镜像跑 `inject 20`，`attempts_to_ok` 应从
  **-1（旧驱动：10 次尝试从未恢复）** 变成 **≈1（新驱动：下一次事务的 `recover()` 就清掉 AF 并重配外设）**。
  这一条是这次加固在真硅上的直接证据。

### 9.4 这次加固**没有**覆盖的三种情形（verifier 复核，必须写明，别把"空转被消掉"说过头）

- **R1：只有"错误标志置位"那条路被消掉了；"安静卡死"仍是 64ms/次。**
  `AF/BERR/ARLO/OVR` 全为 0 的卡死（例如从机把 SCL 拉住但没触发 BERR）依旧会轮询满 `kEventWaitLimit`。
  而新的自愈在那种情形下会**放大**工作量：一次 `tryInit()` ≈10 次事务 × (recover ≈0.1ms + 空转 ≈64ms) ≈ 0.65s，
  每 10 次失败触发一次，发生在 prio 22 的 io 线程里 ⇒ 安静卡死期间该线程接近饱和。
  **这不是回归**（改前是 ~80% 忙且永不恢复），但"空转被压到 µs 级"只对**有标志**的情形成立。
  可选缓解（本次**没做**，因为它要动共享驱动的常量、需重新上板 A/B）：把 `kEventWaitLimit` 从 200000
  降到 ~20000（≈6.4ms，仍是 100kHz 下单字节 90µs 的 70 倍余量）。**注意不能用"墙钟上限"替代**：
  迭代次数对 RT-Thread 抢占是免疫的，墙钟上限会在被抢占时误判超时。
- **R2：自愈失败后错误码会从 0x404 变成 0x0403。** `tryInit()` 失败会把 `initialized` 置 false，
  之后 `read()` 走 `dlx_bmp388.hpp:497-500` 直接返回 `BARO_CALIB_INVALID(0x0403)`，不再是 0x404。
  健康位已 false 不会多报，但**现场分析"0x404"时要记得这个切换**。
- **R3（有意的取舍）：陈旧标志会"毒"一次事务。** 若上一个事务结束时 SR1 里还留着 OVR/BERR，
  下一个事务的第一次 `waitEvent` 会在 i=0 立即失败（然后 `recover()` 清掉）⇒ 把"静默的错误数据"
  变成"一次可检测的失败"，方向更好，但它确实会多一次失败事件。

### 9.5 上板 A/B 的判据（重烧后一条命令就能验）

重烧 bench（新镜像 hex ≈165,590 B，含本加固）后跑 `inject 20`：

| 观察 | 旧驱动（已测） | 新驱动（预期） |
|---|---|---|
| `attempts_to_ok` | **-1，20/20**（10 次尝试从未恢复） | **=1**（下一次事务的 `recover()` 就清掉 AF + 重配外设） |
| `post_af` | 1 | 1（注入处**不**清标志，故意保留诊断） |
| 紧随的 `recover@post-inject` | `sr1_before=0x0500` → `sr1_after=0x0501`（AF/BERR 还在）、`next_ok=0` | `sr1_before` 带 AF/BERR、**`sr1_after=0x0000`**、`next_ok=1` |
| `[fail] durUs` | ≈64ms | 个位数 µs |

**判据**：≥19/20 为 `attempts_to_ok==1` **且** `sr1_after==0x0000` ⇒ 加固生效；
若仍出现 `-1` ⇒ "`I2C_Init` + 清标志能救回来"这个结论要重写（那就回到 R1 的讨论）。

### 9.6 还没做的（保留为建议）

## 10. 覆盖不到的部分（别把本文档说过头）

离线证据的**承载假设**先集中列一次（verifier 在 `test-data/baro_bench/verification.md` §6d/§7 逐条核过）：

- **`test/iic_error_recovery_test.cpp` 的 `KNOWN-GAP` 是"建模条件下的复现"，不是硬件证据。**
  它的承载假设是替身里"`AF=1` 时 START 不产生 SB"（`test/iic_stub/stm32f4xx.h:270-274`，依据 RM0090 §27.3.7）。
  它能证明"**若** AF 阻塞则下一次事务连 START 都等不到"，**不能**证明真硬件上 AF 一定阻塞 ——
  那只能靠台架的 `inject` 实验（替身里也留了 `hmAfBlocksNextTransfer` 开关做敏感性）。
- **`bmp388_error_provenance_test.cpp` 的 comp 用例是人为构造的**（标定 P1 置负 + 数据全 FF），
  它只证明"comp 路径可达且与 tx 路径互斥"，**不证明**现场那批 0x404 属于 comp 类。现场比例仍要台架 `kind` 计数。
- **反汇编估算 30~55ms 是量级（±50%）**：`I2C_CheckEvent` 有快路径、APB1 桥同步开销没有精确定标；
  可靠的是硬下界 ≈12ms 与"tx 类失败不可能是 µs 级"。权威值由台架 `durUs` 给出。
- **"同窗"的统计只在一份日志里有判别力**（22:28，富集 6.4×）；其余日志要嘛 base rate 饱和、要嘛没有功效。
  拿"旁边没有 0x204"当反证是**逻辑错误**（§1.1 结论 4）。
- **`[Perf] 主循环 最大` 判不了 H1**：控制环(prio 10)本来就高于 `sns_baro`(22)，这个检查只排除
  "全局 / prio≤10 停顿"；唯一能推翻 §3.3 的反例是控制环与气压计线程之间存在阻塞依赖（锁/阻塞信箱），
  日志既没反例也没证明没有。

其余覆盖不到的东西：

- **H4 的自动化判据已补齐（r2）**：`[fail]` 行尾现在带**失败当刻**的 PB6/PB7 电平（`scl/sda`，取自与 `sr1/sr2`
  同一个快照块），`run_baro.py` 把它写进 `fails.csv` 并在 summary 里给出 `(scl,sda)` 组合分布 +
  "`scl=0` 或 `sda=0`"行数与双 0 行数；判读文案是非因果的（"可能被从机拉住"、"单次不足以定性"、
  "结合 `[recover]` 的 `next_ok`"）。**残留**：这两列在解析器里是**可选**的（为了能离线重放 r1 老日志），
  所以一条**被截断的 r2 行**会解析成"有效但电平空"，让"带电平样本数"静默偏少——summary 把该样本数与
  `fail` 总数并排给出，偏差可见。要更严就在门禁已确认 r2 的前提下把它们改必填。
- **`irqblock` 的 1MHz 假设已硬化**：原来 `prescaler = timClock/1e6 − 1` 隐含"timClock 是 1MHz 整数倍"
  （本板 `84MHz/(83+1)` 精确等于 1MHz，有真机日志的 `HCLK=168MHz/PCLK1=42MHz` 佐证）；
  现在不整除时 `cmdIrqBlock` 会在**打印之前**拒绝并打 `[err] bad-arg irqblock-clock timClock=<n>`，
  不再"打印请求值、硬件按截断值跑"。`off` 不受限。
- **开机 `init` 的 5s 超时没有实测**：本机无真板，这个数值是估的。
  `run_baro.py` **没有** `--init-timeout` 参数（那是 owner 提议、未实现）；真机上若气压计首次应答慢，
  需要现场确认 5s 够不够。

- **示波器级证据**：400kHz 的上升沿/眼图、上拉阻值、SCL 被拉伸的具体波形，台架测不出来，只能靠"降速后失败率是否归零"
  间接推断。
- **真机 RT-Thread 抢占时序**：台架是裸机 + 阻塞式命令，**没有**复现 `sns_baro(22) 空转 → link_tel(24) 饿死` 这条链；
  §3.3 的量级只能用"事务耗时 + 优先级表"推。要收口现场还需要审计 §210-215 的 Phase 0 观测
  （0x404 边沿带 ms 时间戳 + 该次 `read()` 耗时 + `rt_sem_take` 偏差，同一时基），本次没做。
- **事务中途被打断（H7）在台架上能复现，但要看清口径**：`irqblock` 的实现是 **TIM7 更新中断里忙等**
  （不是主循环 `__disable_irq()`——那条路延迟的是主循环自己的下一轮轮询，插不进正在进行的事务），
  所以它确实能在一次 I2C 事务中间抢占。代价：ISR 忙等本身会污染同时段的 `durUs/gapUs` 读数，
  判 H7 时要以 `kind=comp` + `sr1` 的 OVR 位(0x0800) + `raw` 字节指纹为主，别只看耗时。
- **D 来源（`app_sensors.hpp:546`）**：按 §2 的推导它在当前驱动下**不可达**（防御性代码），而且台架固件也**不加载 app 层**，
  所以它既不会出现在台架日志里，也不该被算进运行期假设空间。
- **BMP388 自身状态**：`ERR_REG`/`STATUS` 的异常（例如 `conf_err`）本次只在失败行里顺带记 `status` 字节，
  没有做成专门的器件自检命令。
