# flash 偶发读不出 ID + SimpleLog 异常 —— 台架定位与修复记录（2026-10-18）

工具：ST-Link（pyOCD，`tools/flash_bench/`）+ COM11（2 Mbaud）+ 主机日志（`H:\workspaceData\flight-logs`）。
本文只记**证据**与**验证**；“怎么改”见 `notes_fw.md` / `notes_host.md`。

## 1. 结论速览

| # | 现象 | 结论 |
|---|------|------|
| A | `[Flash] 识别失败(JEDEC=171717)`、`SR1=0x17` | **芯片没在驱动 DO（MISO 悬空）**，不是型号不对、不是坏片。0x171717 是 5.25 MHz 下悬空 MISO 的采样特征（2 MHz 下采到 0x000000）。 |
| A' | `[Flash] init=FAILED err=0x0103 用时=0ms` | `flash.init()` 刚过 JEDEC，1 ms 后 `FlashManager::checkHardware()` 再读 JEDEC 失败。同一芯片两次读结论相反 ⇒ 芯片**瞬时不响应**；固件零重试。 |
| A'' | 根因（硬件侧） | 本板 W25Q128 的 **/CS(PD1) 没有外部上拉**：MCU 复位期间 PD1 浮空，实测默认电平 = **低**（SCK/MISO/MOSI 同样浮低）。芯片在“被选中”状态下经历上电/复位，SCK 上的噪声可能被当成时钟灌进杂散指令；随后芯片忙自己的事（量级 0.1 s ~ 数秒，与扇区/块擦除同量级）而拒绝 JEDEC。 |
| B | 自检说 `flash=OK` / `文件系统就绪 会话=0 预留=0` | 固件把 `fs.init()` 的失败**吞成 SUCCESS**，上层只看指针非空。飞行模式可解锁，但每条日志 `FLASH_NOT_READY` 被静默丢弃 —— **黑匣子坏了还照飞**。 |
| C | “SimpleLog 好像缺了几行” | 固件 `char[160]` 行缓冲截断（丢行尾 `\r\n`、可切断 UTF-8 汉字）＋“补偶数长度”的空格补在 `\n` **之后**（空 `[INFO]` 行）＋上位机每帧一个协程（行序乱）。**固件侧没有丢行**（自报文本丢 0/0，两次启动逐行 diff 无缺）。 |

## 2. 台架原始证据

### 2.1 芯片是好的、型号对
RAM 探针（`fw_flash_sr.c`，直接读寄存器）：
```
JEDEC = 0xEF4018   (Winbond W25Q128JV)
SR1   = 0x00
SR2   = 0x02       -> bit1 QE=1  => /HOLD、/WP 功能被禁用（不是 -IN/-JQ）
SR3   = 0x60       -> DRV=11（默认）
```
⇒ “/HOLD 悬空”这一类解释可以排除。

### 2.2 “不响应”时的总线状态
`fw_flash_gap.c` / `fw_flash_recover.c`（复位后跑 RAM 程序，复位 ≠ 给 flash 断电）：
```
seed  JEDEC = 0xEF4018        ← 第一次事务正常
next  JEDEC = 0x000000  x N   ← 之后全部 0x000000（MISO 悬空 = 芯片没驱动）
SR1         = 0x00            ← 读状态也不应答
（等待 ~10 ms 后）JEDEC = 0xEF4018   ← 自己恢复
```
- 同样的 RAM 程序**跑在 168 MHz / 5.25 MHz 时 4200 次连续读 0 错误**；跑在复位后的 16 MHz（SPI 2 MHz）时才出现上表。⇒ 现象与“复位事件 + 总线时序”，不是“读次数多了把它读坏”。
- `fw_pin_levels.c`（只开 GPIO 时钟、四个脚全做浮空输入）：
```
/CS  PD1 = 0   （内部下拉仍 0，内部上拉才 1）  ⇒ 板上没有外部上拉
SCK  PB10= 0
MISO PC2 = 0
MOSI PC3 = 0
```
### 2.3 固件启动时复现（同现场）
重刷**未修改**的固件后，连续复位 8 次里复现 1 次：
```
[Flash] 识别失败(JEDEC=171717)          ← 现场同款
（1 s 后）只读探测 JEDEC=0x171717        ← 还在忙/还在不响应
（再下一次启动）[Flash] init=OK 会话=12 用时=68ms
```
RAM 程序把 flash 弄“哑”之后，紧接着启动固件也会打印同样的 `0x171717` —— 说明这是**芯片的真实状态**，不是日志假象。

## 3. 修复与验证

### 3.1 改了哪些（详见各文件内注释）
| 文件 | 改动 |
|------|------|
| `DL_LIB/W25Q128/dlx_w25q128.hpp` | `init()` 带**有限重试**：每次失败先 `66h/99h` 软复位 + `ABh` 唤醒 + 等 tPUW，再读 JEDEC；写状态寄存器后**回读确认** SR1=0；新增 `lastJedecId()/lastInitAttempts()` 供日志打印。 |
| `DL_LIB/W25Q128/dlx_w25q128_config.h` | 重试参数（9 轮 × 100 ms ≈ 1 s 预算）+ 说明。 |
| `DL_LIB/W25Q128/dlx_flash_manager.hpp` | `checkHardware()` 重试 3 次（修“刚过 JEDEC 又立刻失败”）。 |
| `release.cpp` | ① **main() 第一件事**把 /CS 驱动为高（把浮空危险窗口从整段启动期压到几条指令）；② `bringUpFlash()` 失败**不再吞**：飞行/调试模式 `app.fs=nullptr`，管理模式保留句柄以便恢复；③ 日志统一带 **JEDEC 实值 + 轮次**；④ LogManage 失败时不再“无限闪灯”，仍进管理模式（格式化是唯一恢复入口）；⑤ `err` 初始化。 |
| `app/control/app_flight_stack.hpp` | `flash=OK` / `文件系统就绪` / `启动自检结束 flash=文件系统` / `flashOk` 位全部改判 **`fs->isReady()`**。 |
| `app/runtime/release_header.h` | 新增 `sanitizeTextLine()`：截断后**补回 `\r\n`**、截断点退到 **UTF-8 边界**、**不再补空格**。 |
| `app/log/app_log_thread.hpp` | 同样走 `sanitizeTextLine()`；`[Link]` 行拆成两条（186 B → 92 B + 108 B）。 |
| `app/control/app_flight_stack.hpp` | `[Boot] 进入串口调试模式…` 拆成两条（168 B → 96 B + 74 B）。 |

### 3.3 上板验证（刷入修好的固件，测完已刷回原版）
- 8 次启动全部 `init=OK`；其中 **1 次日志显示 `识别轮次=2`** —— 第一轮读到坏 ID，**重试把它救回来了**。
- 另 1 次（重刷后首启）芯片持续不响应约 1 s，5 轮重试（当时配置 8 ms 间隔）没等到；修好后的诚实降级可见：
```
[Flash] 识别失败: JEDEC=0x000000(期望 0xEF4018) 试了 5 轮 用时=91ms
[Flash] 本次运行没有可用的 flash 文件系统: 日志改走串口; ...
[Boot] BMI088=OK BARO=OK flash=-
（1 s 后）[Dev ] W25Q128 : 只读探测 JEDEC=0xEF4018 识别=有应答 SR1=0x00
[Boot] ===== 启动自检结束: ... flash=不可用(见上面的 JEDEC/err) =====
```
- 文本行验证：`U+FFFD 0 条`、`>161 B 的行 0 条`、`只有空格的“空行” 0 条`（修改前每次启动 2~26 条）。

## 4. 还需要做的（硬件）

1. **给 flash 的 /CS 加 10 kΩ 上拉到 3.3 V**（最好 SCK/MOSI 也各自加，或至少在 /CS 上）。这是把“复位/上电期间浮空”彻底消掉的唯一办法；固件里的“main() 先拉高 CS”只能在 MCU 跑起来之后生效，复位期间救不了。
2. 若不想改板：保持本次的“重试 + 诚实降级”。重试预算已按实测的 ~1 s 给足；若还想更稳，可把 `W25Q128_ID_ATTEMPTS` 再调大。
3. 现场那次日志里的固件与工作树**不是同一版构建**（E220 机型行被拆成 3 行、`flash=-` 等），复现/验收请用当前工作树重新编译后刷写。
4. 顺带建议：把 `[Flash]` 相关日志作为台架必看项；`识别轮次>1` 就说明芯片当时真的没应答，是硬件隐患的量化指标。
