三种上电模式

Flight 正常飞行
  • 跳线帽 PB8/PB9 没接 → 直接进，完全不看串口
  • 日志写 flash；串口完全静音（ENABLE_EXCEPTION_TEXT() 不调用）
  • 进入 State::Standby（未解锁）
SerialDebug 串口调试（台架）
  • 跳线帽接上 + 上位机 Unlock(mode=1)
  • 日志走串口（与 flash 同格式的原始帧）+ PerfMonitor
  • 不挂载 flash（app.fs=nullptr），只做只读探测
  • 进入 State::Maintenance，允许 ARM + Manual 试车
LogManage 日志管理
  • 跳线帽接上 + Unlock(mode=2)，或等待超时（kWaitTimeoutMs=0 ⇒ 实际一直等）
  • 死循环在 runLogManage()，不进 FlightStack，物理上不可能输出电机
  • 可列/删/回传/格式化 flash；收到 Unlock 后返回目标模式
注意：cfg::ground::kWaitTimeoutMs 若为 0，超时分支永不成立 ⇒ "默认落到 LogManage" 这条注释在配置为 0 时不成立，会一直等上位机。

最重要的两条调度事实
  • main 线程是应用层最高优先级（10），比所有采集/链路/日志线程都高。 因此控制环永远不会被其它线程抢占 —— 它只会被中断抢占。这解释了为什么工程里大量"读一个 32/16 位对齐量而不加锁" 是安全的（写者是低优先级线程，根本插不进来）。
  • 反过来，采集线程（22）会抢占链路线程（24）与日志线程（26）；链路线程会抢占日志线程。 所以"日志线程跑到一半被链路/采集线程打断"是常态，而它进临界区的地方正是为了让控制环与链路侧看到一致状态。

时间分配（每 2 ms 控制周期内的节拍）

  • 0 µs — SysTick（1 kHz）进 rt_tick_increase()；每 2 个 tick 到期 ctrlt ⇒ rt_sem_release(ctrlSem)（在 ISR 里）；ISR 退出时调度 ⇒ 控制环就绪（最高优先级）立即运行。
  • 控制环一步（源码顺序，全部在同一个线程里同步执行）： stepSampleShared（临界区取共享量 + takeTasks）→ stepImu（BMI088 FIFO 阻塞读出 + 2000 Hz 名义积分 + 每 8 个样本一次 15×15 协方差）→ stepObservers（4 路快照，零总线事务）→ stepAssembleInputs → stepStateMachine（失效保护 + 准入 + 迁移 + 效果 + 高度目标 + 油门交接）→ stepControl（四档控制律 + 混控 + DShot 预载）→ stepPublish（遥测/快照/日志位）→ stepLog（每 20 ms 飞行 / 10 ms 调试入队一条）→ stepPerf（DWT 统计，每 200 ms 汇总）。
  • 谁在这期间插入：DShot DMA 完成中断（P1_S0，每帧 22 bit < 1 µs 量级，频率 = 帧率）、 USART1 RXNE（2 Mbaud ⇒ 每 5.2 µs 一个字节，若上位机在灌数据）、 链路 USART3 RXNE（57600 ⇒ 每 173 µs）、EXTI3（测距 20~50 ms 一次）、SysTick（每 1 ms）。
  • 预算：cfg::log::kPerfWarnUs = 800 µs；perfWarmup = 5 圈不计入统计 （前几圈含 FIFO 积压 + EKF 首次整定，实测能到 5 ms）。
  • 超时的后果：ctrlSem 是计数信号量，若某一圈超过 2 ms， 下一次 release 会让信号量计数 +1，控制环退出 stepPerf 后立刻又拿到一个 ⇒ 背靠背连跑， 周期漂移而不会报错（只能在 loopPeriodUs / PerfMonitor 里看出来）。

记录帧 = [0xAA][定长结构体][0x00]，提交尾字节最后单独写 1 字节 ⇒ 掉电中断的记录判为"没写完"。 尺寸实算：LogEntry sizeof=172、步长 176 ⇒ 744 条/槽（配置注释里的"885 条"是旧值）； FlashMetaRecord 56/步长 60；FlashParamSlot 268/步长 272；条目区起点 20。 槽头含 slotSeq（全局单调）/ slotIndex（物理号自校验）/ sessionId。

会话与槽预留（日志写路径核心）

  1. init() → findRingBounds() 只扫 127 个槽头（各 1 次 ~20 B 读）求 newest（slotSeq 最大）与 oldest（从 newest 往回 seq 连续减 1，不连续即停）⇒ 内存 O(1)。
  2. startSlot=(newest.index+1)%127；session=max(meta.sessionCounter,newest.sessionId)+1；reservedSlots=clamp(sessionSlotLimit,1,127)。
  3. 擦除量 = reservedSlots − erasedPrefix（erasedPrefix 由元数据反推上次实际用了几槽；不可信时宁可多擦）。
  4. 只给起点槽写槽头，其余预留槽用到再写 ⇒ "最新槽 == 最后真正写过的槽"。
  5. advanceSlot()：本槽 744 条写满取下一槽；slotUsed ≥ reservedSlots 时现场擦该槽（2×64 KB，典型 0.3 s / 最坏 5 s，无进度回调）再写槽头。

风险与待查：这次梳理发现的具体问题

按"多可能真的出事"排序。高 = 有明确的错误路径或竞态窗口； 中 = 设计意图与实现对不上，会导致"改了配置不生效"或"故障静默"; 低 = 整洁性问题 / 死代码。

高 1. 控制环内做 SPI 事务，而 SPI 的忙等没有超时

app_flight_stack.hpp:1087 的 bmi.fifoRead(ac, gy) 是控制环里唯一的总线事务， 而 DL_LIB/dlx_spi.hpp（267/269/282/284/296/298/308/310/319/321/329/331 行）全是 while (SPI_I2S_GetFlagStatus(...) == RESET); —— 无超时、无救出口。

对照：I2C 那条链有 20 万次轮询上界（dlx_iic.hpp），而 SPI 没有。 后果：BMI088 若因片选/接线/供电问题不响应，控制环会永久挂在 stepImu，DShot 停止更新 ⇒ 表现为"飞机没反应"， 而 LED 心跳灯由日志线程维持（HEARTBEAT_MS=500）⇒ 灯还在闪，排查者会以为系统活着。 与项目"驱动层所有忙等都加超时"的目标（stm32f4xx_it.cpp 注释里的 B4/B5 计划）不一致。

高 ★ 控制环每拍还会自旋等中断：Dshot::preloadThrottle()

app_flight_stack.hpp:1740（解锁后每一拍）与 :305（解锁那一拍）都调 dshot.preloadThrottle(motor)，而 dlx_dshot.hpp:187-196 是：

void preloadThrottle(uint16_t v0, v1, v2, v3) {
    while (transferStatus != 0);   // ← 无界自旋，只等 DMA TC 中断递减
    throttle[0..3] = v0..v3; preEncode(); transferStatus = 2;
}
  • 正常情况的自旋 ≈0：上一拍设的 transferStatus=2 需要 2 次 TC 中断（每个 DShot 帧一次）才归零， DShot300 一帧 ≈73 µs ⇒ 约 147 µs 内就会归零，而下次调用在 2 ms 之后。所以它平时不占预算。
  • 但它没有任何超时、没有任何退路：一旦 DMA 停止（stop() 之外的原因）、 或 P1_S0 的 TC 中断被长时间屏蔽/被更高抢占优先级的中断持续压制、或 DMA 因总线错误挂死 —— 控制环就会永久停在这一行。表现与 §风险 1 的 SPI 死等完全一样：电机停在最后一次的 DShot 帧上、 心跳灯（由日志线程翻转）照样闪、串口没有任何线索。
  • 注释里纠结过这一点（dlx_dshot.hpp:179-186：先改成"不等待的最新值优先"，后来又"加上防撕裂"改回自旋）。 防撕裂是对的，缺的是超时 —— 例如"自旋超过 N µs 就放弃本次同步（下一拍还会再试）"， 峰值撕裂缝本来就只会让 ESC 丢一帧。
  • 顺带一个观测性小问题：logDshotTiming() 打印的"理论帧率 = realHz/22" 少除了一次每 bit 的 40 计数 ⇒ 比真实帧率大 40 倍（DShot300 实际 ≈13.6 kHz，代码算出 ≈545 kHz）。 这一行是上电卡死时的唯一定位点，数值得对。

高 2. Flight / SerialDebug 模式下 uartRx 无人排空

uartRx（256B）只在两个地方被消费：decideBootMode() 的等待循环、runLogManage() 的 drainDlx()。 进入 FlightStack 之后没有任何人读它。USART1 RXNE ISR 仍然开着（dlx_usart.hpp:290）， 把字节写进环并忽略 write() 的返回值。所以：

  • 上位机只要在飞行/调试模式下说话，环在几毫秒内即满（2 Mbaud），此后所有字节静默丢弃；
  • 没有计数器能反映"丢了多少"（RingByteBuffer 默认 allowOverwrite=false，满即返回 false）。

建议：要么在进入运行期时关掉 RXNE 并记录一次，要么在 logger 的调试模式分支里 uartRx->reset() 并计数 —— 现状是"看起来有入口、实际是黑洞"。
