# W25Q128 简易文件系统(FlashManager)：日志 + 持久化参数

一句话：把一个 16MB 的 W25Q128 切成"元数据 / 持久化参数 / 日志"三段，日志按"一次上电 = 一个会话"
组织、会话一次占用若干个 128KB 的槽、上电只擦需要回收的槽；参数和元数据用"多槽环形写 + 整扇区轮转擦除"
保证掉电安全和磨损均衡。实现是纯头文件，`DL_LIB` 已在 EIDE 的 `srcDirs` 里，不用改工程配置。

---

## 1. 需求与定位

不做通用文件系统(不要目录、变长文件、碎片整理)，只解决两件事：

1. **运行日志**：一次上电 = 一个日志会话，掉电重启后能接着存，事后能按会话回读(导出/回放/对比)；
2. **持久化参数**：一组数值参数掉电不丢，允许反复改写。

约束来自飞行器本身：擦除会阻塞几十~几百毫秒，**飞行中不能停下来等擦除**，所以"擦"要么放在上电时
(多等一会没关系)，要么属于非正常工况(宁愿丢日志也不要卡控制循环)。

文件：

| 文件 | 内容 |
| --- | --- |
| `DL_LIB/W25Q128/dlx_flash_manager.hpp` | 行为实现(纯头文件) |
| `DL_LIB/W25Q128/dlx_flash_manager_config.h` | 全部约定：段布局、帧格式、结构体、策略、默认值 |
| `DL_LIB/dlx_exception.h` | `FLASH_*` 错误码(0x0100 起，0 保留不用) |
| `main_flash_fs.cpp` | 上板自测(串口打印)，EIDE 里默认排除编译 |
| `test/flashfs_sim/` | 主机端逻辑测试(模拟 Flash，含掉电注入) |

## 2. 存储结构

### 2.1 三段布局(16MB = 4096 × 4KB 扇区)

```
0x000000  元数据段   120KB  30 扇区   多槽环形写，每次 init 追加一条
0x01E000  持久化参数段 8KB   2 扇区   槽位轮转，每次 saveParams 追加一槽
0x020000  日志段   15.87MB 127 槽     每槽 128KB(= 32 扇区)；一次上电(会话)预留若干槽
```

三段的偏移/大小都在 config 里由常量推导，并 `static_assert` 三段之和正好铺满整片 Flash。

元数据段给到 120KB 是故意的：它是"垫磨损"用的(见 4.4)，实际占用很小，多出来的都是磨损余量。

### 2.2 帧格式(四种记录统一)

```
[0xAA][定长结构体][0x00]
```

| 字节 | 含义 |
| --- | --- |
| `0xAA` | 帧头：用来判断"这个位置写过记录没有"(擦除态是 `0xFF`) |
| 定长结构体 | `FlashMetaRecord` / `FlashParamSlot` / `FlashLogSlotHeader` / `LogEntry` |
| `0x00` | **提交标记**：写完"帧头+结构体"之后，单独写这 1 个字节 |

- 掉电发生在提交之前，尾字节还是 `0xFF` → 判为"没写完"，读取时直接当作数据末尾，下次原地重写；
- 结构体里都有 `uint16_t crc`(固定偏移 2)，覆盖除自身外全部字节 → 位翻转能被发现；
- 帧尾负责"完整性"，CRC 负责"正确性"；
- 重写同一条记录是安全的(Flash 只能把 1 写成 0)，所以写失败后原地重试不会写坏。

### 2.3 段内通用机制：多槽环形写(元数据段 / 参数段)

- 段内按"槽"顺序写：槽大小 = `align4(sizeof(结构体) + 2)`，一个 4KB 扇区放整数个槽，剩余尾部空着；
- 每写一个槽，序号 +1；读的时候取"序号最大且 CRC 通过"的那个槽；
- 只有当写入位置正好落在某个扇区的第 0 槽时才擦那个扇区 → **擦除在整段的扇区之间轮转**；
- 掉电最多丢掉"当前正在写的那一个槽"，上一个有效值始终在。

| 段 | 槽大小 | 每扇区槽数 | 总槽数 | 一次擦除覆盖 |
| --- | --- | --- | --- | --- |
| 元数据(56B 记录) | 60B | 68 | 2040(30 扇区) | 68 次上电记录 |
| 参数(260B 数据) | 272B | 15 | 30(2 扇区) | 15 次参数保存 |

## 3. 槽与会话模型(日志段，核心)

### 3.1 槽(slot)

日志段 = **127 个槽**，每槽 **128KB = 32 个 4KB 扇区**。槽是"擦除的最小管理单位"：
擦一个槽 = 2 次 64KB 块擦除；槽内则是顺序编程，不需要再擦。

槽内布局：

```
offset 0                          槽头记录(AA + FlashLogSlotHeader + 00 = 18 字节，占用到 20)
offset 20 (FLASH_LOG_ENTRY_AREA_OFFSET)
  ├─ 条目 #0 :  AA + LogEntry(144B) + 00  + 补齐  → 共 148 字节(FLASH_LOG_ENTRY_STRIDE)
  ├─ 条目 #1 :  同上
  ├─ ...
  └─ 条目 #884 (每槽 885 条：(131072-20)/148)
    剩余不足一个步长的尾部不写，保持 0xFF
```

### 3.2 槽头(FlashLogSlotHeader)

每个槽的第一条记录，`init()` 擦完槽立刻写它。字段：

| 字段 | 说明 |
| --- | --- |
| `slotSeq` | 槽使用序号，全局单调递增；**最大的就是最新写过的槽** |
| `slotIndex` | 槽在日志段里的物理序号(地址与内容是否对应的自检) |
| `sessionId` | 本槽属于哪个会话；一次上电 = 一个会话，一个会话可占多个连续槽，它们的会话号相同 |

### 3.3 条目(LogEntry)

`0xAA + 结构体 + 0x00`，步长固定 148 字节；前 12 字节由管理器填/校验：
`type`(预留扩展)、`reserved`、`crc`、`sessionId`、`seq`(会话内序号，从 1 开始)；其余是业务字段。

- 读的时候从条目区起点按步长走：帧头/帧尾/CRC/会话号任一不符就**停止**(截断式)，之前的数据仍然有效；
- 因为步长固定，读到 `0xFF` 就说明这个槽写完了，不需要额外的长度字段。

### 3.4 会话与预留区

- **一次上电 = 一个日志会话**，`init()` 时开一个新会话；
- 新会话从"最新槽的下一个槽"开始，一次**预留 N 个槽**(N = `FLASH_LOG_SESSION_SLOT_LIMIT`，默认 32 = 4MB)；
  运行中还可以用 `dropSessions()` 丢掉最老的历史会话，把它们腾出的槽**并进当前会话的预留区**(见第 6 节)；
- `init()` 保证这 N 个槽**擦干净**(见 4.2)，之后写满一个槽就自动接着用预留区里的下一个槽——
  **会话内部不再擦除**，所以飞行过程中不会突然卡几百毫秒；
- 预留区里"没写到、没写槽头"的槽不会被扫描到 → "最新槽"永远等于最后真正写过的槽，
  下次上电起点算得对，会话列表里也不会冒出空会话。

### 3.5 序号体系(别搞混)

| 序号 | 存在哪 | 含义 | 用途 |
| --- | --- | --- | --- |
| `slotSeq` | 槽头 | 槽被使用的次数(全局单调) | 找最新槽、判断日志环边界 |
| `sessionId` | 槽头 + 每个条目 | 第几次上电(严格递增) | 把条目归到某次上电；清日志后不重用 |
| `seq` | 条目 | 会话内第几条(从 1 开始) | 按序号读、断点续读 |
| `seq`(元数据) | 元数据记录 | 元数据写的次数 | 取最新元数据 |
| `seq`(参数槽) | 参数槽 | 参数写的次数 | 取最新参数 |

### 3.6 不变式(整套逻辑依赖这几条)

| 编号 | 不变式 | 谁在维护 |
| --- | --- | --- |
| I1 | 用过(有合法槽头)的槽在环里是**连续一段**，其余是已擦的 | init / advanceSlot / dropSessions |
| I2 | 用过槽的 `slotSeq` **连续递增，没有空洞** | startSession 用"被丢掉的第一个序号"、advanceSlot +1 |
| I3 | 最新槽 = `slotSeq` 最大者；写指针 = 最新槽的下一条记录/下一个槽 | appendLog |
| I4 | 会话开始时，预留区 N 个槽必然处于**已擦**状态 | 4.2 的按需擦除 |
| I5 | 元数据里的预留区信息只有在能自校验时才采信，否则退化为"多擦" | init 的 erasedPrefix 推导 |

## 4. 擦写管理(重点)

### 4.1 擦除入口一览

| 入口 | 擦什么 | 什么时候 | 典型耗时 | 进度回调 |
| --- | --- | --- | --- | --- |
| 首次 `init()`(未建立系统) | **整片** 256 个 64KB 块 | 第一次上板 / `format()` 之后 | 几十秒 | ✅ 256 次 |
| 平时 `init()` | 只擦"需要回收的旧槽"：位置在上次预留区**之后**、环形最旧的一端；数量通常 = 上次会话用掉的槽数(见 4.2.1) | 每次上电 | 1 槽 ≈ 0.3s | ✅ 每 64KB 块一次 |
| `appendLog()` 换槽 | 预留区内：**不擦**；超出预留区：擦下一个槽 | 覆写策略下写超预留区时 | ≈ 0.3s | ❌ 静默(非正常工况) |
| `dropSessions()` / `clearHistory()` | **最老**的若干个会话占用的槽(腾出来并入当前会话预留区) | 手动清历史 | 槽数 × 0.3s | ✅ |
| 元数据/参数写入 | 轮到的那个扇区(整段轮转) | 该扇区槽用完时 | ≈ 45ms | ❌ |

### 4.2 init 的按需擦除(关键推导)

新会话需要 `[startSlot, startSlot + N)` 是干净可写的。其中**大部分上次就已经擦好、之后也没写过**，
所以只需要擦真正需要回收的那部分。判断依据是元数据里记的三个数：

```
reserveStartSlot / reserveStartSeq / reservedSlots   ← 上一次会话的预留区信息
```

推导：

```
used_prev      = 最新槽.slotSeq - reserveStartSeq + 1        // 上次会话实际用掉几个槽
erasedPrefix   = reservedSlots - used_prev                   // 上次预留区里"已擦且没写过"的槽数
真正要擦的槽数 = N - min(erasedPrefix, N)
```

**自校验与退化**(宁可多擦，绝不漏擦)：

- 只有当 `1 ≤ used_prev ≤ reservedSlots` 时才采信(说明元数据就是上一次会话留下的)；
- 元数据是更早一次上电留下的(比如上次在写槽头/写元数据之间掉了电) → `used_prev` 会偏大 → 少跳过一些槽 → 多擦几块；
- 上次是覆写策略、冲出过预留区 → `used_prev > reservedSlots` → 直接 `erasedPrefix = 0`，整个预留区全擦；
- 刚整片擦除过(新建) → `erasedPrefix = 127`，一个槽都不擦。

#### 4.2.1 澄清：擦的不是"上次会话占用的槽"

容易被这句话绕进去：擦除的**数量**通常等于上次会话用掉的槽数，但擦除的**位置**完全不是那些槽。
上次会话占用的槽是最新的日志数据，**一个字节都不动**。

设上次会话预留 `R_prev` 槽、实际用掉 `U_prev` 槽(起点 `prevStart`)：

```
 [最新会话占用的槽][上次预留区没用的空槽][ 本次要擦的旧会话 ][…… 更旧的会话 ……]
  prevStart        prevStart+U_prev     prevStart+R_prev     再往后等下次上电
  ↑ 最新数据, 保留   ↑ 上次擦过, 跳过      ↑ 本次回收(U_prev 个)
```

| 区域 | 是什么 | 本次处理 |
| --- | --- | --- |
| `[prevStart, prevStart+U_prev)` | 上次会话写下的日志(最新数据) | 不擦，保持可读 |
| `[prevStart+U_prev, prevStart+R_prev)` | 上次预留区里没用到的空槽 | 跳过不擦(上次 init 已擦好) |
| 紧随 `prevStart+R_prev` 之后的若干槽 | 环形顺序上**最旧**的一端的旧会话 | **本次擦掉，回收成写入空间** |

数量为什么正好是 `U_prev`：环形容量固定(127 槽)，写指针往前推进多少，后端就得回收多少；
一般式是 `需要擦 = max(0, U_prev + R - R_prev)`——预留槽数没变时就是 `U_prev`，
把 `setSessionSlotLimit()` 调大就会多擦几个(新纳入预留区的那部分)，调小可能一个都不擦。

另一个细节：**环形还没写满的第一轮**(上次格式化后还没用够 127 槽)时，这段"待回收区"其实是
从没写过的空槽，擦它属于多余的等待(无害)；数量同样是 `U_prev`。等环满了才是真正回收最旧的会话。

实测(主机测试 [11]，预留 8 槽)：

| 上次会话实际用量 | 改之前 | 现在 |
| --- | --- | --- |
| 1 个槽 | 擦 8 槽(16 块, ≈2.4s) | **擦 1 槽(2 块, ≈0.3s)** |
| 2 个槽 | 擦 8 槽 | **擦 2 槽(4 块)** |

### 4.3 会话内部换槽：不擦

`appendLog()` 发现当前槽写满(`slotEntries == 885`)时：

1. 如果 `slotUsed < reservedSlots`(预留区还有) → 直接写下一个槽的槽头，**不擦除**，写入成功，`err = FLASH_OK`；
2. 如果预留区用完：
   - `Halt` 策略 → 返回 `FAILED` + `FLASH_LOG_FULL`，数据保持完整；
   - `OverwriteOldest` 策略 → 擦掉下一个槽(那是最旧的会话，≈0.3s) → 写槽头 → 继续写，
     本次 `err = FLASH_LOG_OVERWRITTEN`(提示性异常，**写入本身成功**)。

> 这个"覆写"提示只在真的擦掉旧会话时给；预留区内正常换槽不再误报(已修)。

### 4.4 元数据/参数段：整扇区轮转擦除

写入位置走到某个扇区的第 0 槽时，先擦该扇区(其余槽都已经用过、属于最老的记录)。效果：

| 段 | 擦除周期 | 每个扇区承担 |
| --- | --- | --- |
| 元数据 | 每 68 次上电 | 120KB 分给 30 个扇区轮流 |
| 参数 | 每 15 次保存 | 8KB 分给 2 个扇区轮流 |

按 W25Q128 每扇区 10 万次擦写寿命算，元数据段 30 扇区 × 68 次 ≈ **200 万次上电**才用完一轮，
参数同理够用一辈子。这就是"元数据段给 120KB"的原因——它换的是擦写寿命和数据安全。

### 4.5 擦除粒度与耗时

| 操作 | 粒度 | 典型 | 数据手册最坏 |
| --- | --- | --- | --- |
| 扇区擦 | 4KB | 45ms | 400ms |
| 块擦 | 64KB | 0.15s | 2s |
| 一个日志槽 | 128KB = 2 × 64KB | ≈0.3s | 4s |
| 整片(256 × 64KB) | 16MB | 几十秒 | — |

### 4.6 掉电发生在擦除中途会怎样

| 掉电时刻 | 现场状态 | 下次上电 |
| --- | --- | --- |
| 擦槽中途 | 该槽部分擦除(有的扇区 0xFF、有的还是旧数据) | 该槽没有合法槽头 → 不算会话数据；下次需要它时按 4.2 重新擦，所以不会写进"半擦"的槽里 |
| 擦完、还没写槽头 | 槽干净，元数据还是旧的 | 起点/用量按旧的元数据重算 → 最多多擦几块，不会漏擦 |
| 写完槽头、还没写元数据 | 会话已存在，元数据旧一代 | 同上，多擦几块 |
| 写条目中途 | 尾字节仍 0xFF → 该条被丢弃 | 从这条位置继续写，之前的条目完好 |

**不会出现"应该擦却没擦"**：所有"跳过擦除"的判断都基于"我们确实擦过、且之后没写过"，
判断条件不成立就退化成全擦。

### 4.7 为什么不把写指针存在元数据里

- 每写一条日志都回写元数据 → 元数据段被反复擦，磨损集中；
- 现在写指针完全靠**扫槽头**推出来(127 次小读，几毫秒)，元数据只在"换会话"时写一条；
- 代价是上电要扫一遍槽头，但这点时间相对擦除可以忽略。

## 5. 写满策略

`init(policy, ...)` 指定，运行中可用 `setFullPolicy()` 切换：

| 策略 | 预留区用满后 | 返回值 | 日志结果 |
| --- | --- | --- | --- |
| `FlashFullPolicy::Halt` | 拒绝写入，等下次上电(新会话)或切策略 | `FAILED` + `FLASH_LOG_FULL` | 保留本次已写数据和全部历史会话；**单次上限 = N 槽** |
| `FlashFullPolicy::OverwriteOldest` | 擦掉最旧的会话继续写(可连续跨多个会话) | `SUCCESS` + `FLASH_LOG_OVERWRITTEN`(只在擦那一步) | 始终保留最新的数据，最老的被循环覆盖 |

两种策略下**读取逻辑完全一样**：一个会话跨多个槽时按 `sessionId` 相同、`slotSeq` 连续把它们串起来。

Halt 策略下如果还想写更久，不必切策略：先 `clearHistory()` / `dropSessions(n)` 把最老的历史丢掉、
把槽并进本次会话（地面时做，几秒），之后本次会话的上限就变大了。

## 6. 清理日志

**模型是环形队列，不是栈**：写指针只往前，自动回收的永远是队头（最老）那一段。
所以 `dropSessions()` 丢的也是**最老**的会话，腾出来的空间直接给"当前正在写的这次会话"用。

```cpp
fs.dropSessions(1, err);             // 丢掉最老的 1 个会话
fs.dropSessions(3, onBusy, err);     // 丢掉最老的 3 个, 可带点灯回调
fs.clearHistory(onBusy, err);        // 清空全部历史(只留当前会话), 等价 dropSessions(FLASH_DROP_ALL_SESSIONS)
```

- **丢队头**：从最老的一端往后数够 `count` 个会话就停，擦掉它们占的槽；不挖洞、不需要额外记账；
- **写指针不动**：当前正在写的这次会话不会被重开（它永远是队尾），会话号也不变；
- 腾出来的槽**并入当前会话的预留区**（`reservedSlots += 被丢掉的槽数`），于是：
  - 本次会话的 `sessionEntryLimit()` 变大，可以一直往下写——**飞行中依然零擦除**；
  - 空间账守恒：丢掉多少槽，本次会话就能多写多少槽；
  - 同时补写一条元数据，让下一次上电也知道这段是干净的，不必重复擦（见 4.2）；
- 当前会话是队尾，**永远不会被 `dropSessions()` 丢掉**；`count` 超过历史会话数时按实际能丢的来；
- 想连当前会话的数据也清掉（恢复出厂）用 `format()`，代价是参数段一起没了。

典型用法：

| 场景 | 调用 |
| --- | --- |
| 导出完日志，准备下一轮飞行 | `fs.clearHistory(onBusy, err)`（清历史，当前会话继续用） |
| 只想丢掉最老的一两次上电 | `fs.dropSessions(2, err)` |
| 连参数一起恢复出厂 | `fs.format(err)` 然后重新 `init()` |

> 早期版本这里是"丢最新 N 个会话 + 回退写指针 + 重开会话"（栈式撤销语义），已按环形队列的思路去掉。

---

## 7. 掉电与损坏恢复(读侧)

- **半条记录**：尾字节 `0xFF` → 丢弃，该位置就是本次会话的数据末尾；
- **位翻转**：CRC 不过 → 从这条起停止返回(截断式)，之前的仍可读；
- **槽头坏了/写了一半**：帧尾或 CRC 不过 → 该槽不算数据(不参与"最新槽"的判断)；
- **元数据段全坏**：认为"没有文件系统" → 会走一次整片擦除(这是唯一会丢数据的自动路径，属预期语义)；
- **元数据能读但布局指纹不符**(改了 `LogEntry` 大小、改了段大小、格式版本变了) → 返回 `FLASH_GEOMETRY_MISMATCH`，
  **不自动重建**，确认要重来就 `format()`。

---

## 8. 持久化参数

- `FlashParamData` 整体作为一个槽写入(默认 260B：`version` + 64 个 float)，`saveParams()` 每次追加一个槽；
- 读 `loadParams()` 扫全部 30 个槽取序号最大者；每 15 次保存才擦一次扇区，且在 2 个扇区之间轮转；
- `peekParams()` 不需要 `init()`，上电早期就能读(用来决定"本次要用全量日志还是精简日志")；
- 一条都没有时返回 `FLASH_PARAM_NOT_FOUND`，上层用默认值。

---

## 9. 元数据段

每次 `init()` 追加一条 `FlashMetaRecord`(56B)：

| 字段 | 用途 |
| --- | --- |
| `magic` / `version` | 判断"文件系统是否已建立"；版本不符就拒绝使用 |
| `seq` | 取最新元数据 |
| `bootCount` | 上电次数(统计) |
| `sessionCounter` | 已分配出去的最大会话号(保证严格递增) |
| `reserveStartSlot` / `reserveStartSeq` / `reservedSlots` | 预留区信息 → 4.2 的按需擦除 |
| `metaSectors` / `paramSectors` / `logSlotSectors` / `logSlots` / `entrySize` / `paramSize` | 布局指纹 |

## 10. 接口

```cpp
FlashManager fs(flash);                                  // flash 需先 flash.init()
ExceptionCode err;

// 上电早期：不用 init、不建会话就能读参数(决定日志档位)
FlashParamData p;
fs.peekParams(p, err);                                   // 没保存过 -> FLASH_PARAM_NOT_FOUND
fs.setSessionSlotLimit(32);                              // 下一次 init 生效(单会话预留 32 槽 = 4MB)

// 初始化：空参 lambda 每擦完一个 64KB 块回调一次(点灯/翻 IO/喂狗)
fs.init(FlashFullPolicy::Halt, [&]{ led = !led; }, err);
// 新建过 -> SUCCESS + FLASH_SYSTEM_CREATED(提示性异常); 已有 -> SUCCESS + FLASH_OK

LogEntry e = {};  e.tickMs = 100;  fs.appendLog(e, err);  // 管理器字段(会话号/序号/CRC)自动填

fs.saveParams(p, err);  fs.loadParams(p, err);

fs.forEachSession(cb, ctx, err);      // 只扫槽头, 很快: 会话号/占用槽数/字节数/是否当前会话
fs.countEntries(sessionId, n, err);   // 某会话条目数
fs.forEachEntry(sessionId, cb, ctx, err);   // 逐条读
fs.readEntry(sessionId, seq, out, err);     // 按序号读

fs.dropSessions(1, err);              // 丢最老的 1 个会话(腾出的槽并入当前会话)
fs.clearHistory(err);                 // 清空全部历史(只留当前会话)

fs.format(err);                       // 整片重建(几十秒, 丢全部数据)
```

其他：`setFullPolicy()`、`isLogFull()`、`currentSessionId()`、`currentEntryCount()`、
`sessionReservedSlots()` / `sessionUsedSlots()` / `sessionEntryLimit()`。

非线程安全：请在同一个上下文(主循环/同一线程)里调用。`FlashManager` 自身约占 280B RAM(收发缓冲)。

---

## 11. 错误码(`ExceptionCode`，0x0100 起)

| 码 | 含义 |
| --- | --- |
| `FLASH_OK` | 无异常 |
| `FLASH_SYSTEM_CREATED` | 未检测到文件系统，已整片擦除并新建(调用仍算成功) |
| `FLASH_GEOMETRY_MISMATCH` | 已有文件系统与当前编译的布局/结构体不符(不自动重建) |
| `FLASH_HARDWARE_ERROR` | 读不到正确的 Flash ID |
| `FLASH_ERASE_FAILED` / `FLASH_WRITE_FAILED` / `FLASH_READ_FAILED` | 硬件操作失败(超时) |
| `FLASH_NOT_READY` | 未成功 init() 就调用其它接口 |
| `FLASH_LOG_FULL` | Halt 策略下达到单次上限，本次写入被拒绝 |
| `FLASH_LOG_OVERWRITTEN` | 已环绕覆写最旧的会话(提示性异常，写入成功) |
| `FLASH_SESSION_NOT_FOUND` / `FLASH_ENTRY_NOT_FOUND` | 找不到指定会话/条目 |
| `FLASH_PARAM_NOT_FOUND` | 参数段还没有可用参数 |
| `FLASH_INVALID_ARGUMENT` | 入参非法(空指针等) |

约定：函数返回 `FunctionResult`(SUCCESS/FAILED)，具体结果与异常通过 `ExceptionCode&` 带出。

---

## 12. 默认数值(改 config 即可)

| 项 | 默认 | 说明 |
| --- | --- | --- |
| `LogEntry` | 144B | 管理器占前 12B，其余业务字段(发布版飞行日志) |
| 条目步长 / 每槽条目 | 148B / 885 | 步长 = 对齐4(帧头+结构体+帧尾) |
| 槽大小 / 槽数 | 128KB / 127 | 日志段 15.87MB |
| `FLASH_LOG_SESSION_SLOT_LIMIT` | 32 (4MB) | 单次会话上限 = 32 × 885 = 28320 条(50Hz 约 9.4 分钟) |
| `FLASH_PARAM_VALUE_COUNT` | 64 | 参数槽 272B，每扇区 15 槽 |
| `FLASH_META_SECTOR_COUNT` | 30 (120KB) | 自动 = 总扇区 - 参数 - 日志，专门垫磨损 |

改 `LogEntry` 字段后：步长/每槽条目/单次上限自动跟着变；结构体大小变了旧数据判为几何不匹配，需要 `format()`。

## 13. 上电时序与耗时

```
flash.init()                        校验 JEDEC ID
fs.init(policy, onBusy, err):
  1. 读元数据段(先扫 30 个扇区首槽, 再细扫最新扇区)   ≈ 几 ms
     没有 -> format(): 整片擦除(256 块, 几十秒, 回调 256 次) + 写元数据
  2. 布局指纹校验 -> 不符则 FLASH_GEOMETRY_MISMATCH
  3. 扫 127 个槽头 -> 最新槽/会话号                  ≈ 几 ms
  4. 擦预留区里"需要回收的槽"(通常 1 个, ≈0.3s, 回调 2 次/槽)
  5. 写起点槽头 + 追加一条元数据
```

## 15. 已知取舍与后续可做

- 记录损坏后该会话从损坏处往后不可读(截断式)——够用，不做逐条跳读；
- 只有一种日志条目结构体，帧里留了 1 字节 `type` 供以后扩展多种条目；
- 覆写策略下"超出预留区"的现场擦除是静默的(属非正常工况)；想避免它就用
  `clearHistory()` / `dropSessions()` 在地面先把最老的历史丢掉、把槽让给本次会话；
- 清理只在"最老的一端"做(环形队列语义)，没有"删掉中间某次上电"的能力；
- 元数据格式版本从 1 提到 2(加了预留区信息与会话计数器)，旧版数据需要 `format()` 重建。
