# DLX 通信协议：由 Kotlin 类生成 C++ / Kotlin 两端代码

一句话：DLX 是一套"**Kotlin 类 = 报文定义**"的协议。Kotlin 侧写一个带注解的 data class，
KSP 处理器同时生成 **C++ 帧收发函数（`dlx.hpp`）** 与 **Kotlin 解码/编码代码**，
两端字段顺序、字节序、CRC 完全由生成器保证一致，所以改协议只改 Kotlin 类，不改 C++。

生成的文件（本工程）：`DL_LIB/dlx.hpp`
文件头写着 `AUTO-GENERATED by the KSP protocol generator`，**不要手改**（会被下次生成覆盖）。

---

## 1. 报文定义长什么样（Kotlin 侧）

```kotlin
class EKF(
    @TargetBasicType(DLXBasicType.FLOAT)
    @FixedLength(4)                     // 定长数组：FloatArray 长度 4
    val data: FloatArray,
    @TargetBasicType(DLXBasicType.FLOAT)
    val height: Float,
    @TargetBasicType(DLXBasicType.FLOAT)
    val vh: Float,
) {
    fun toQuat(): Quat = Quat(data)     // 类里可以带自己的辅助方法，不影响协议
}
```

生成结果（对应 `dlx.hpp` 里的类型 10）：

```cpp
struct EKF {
    ByteBuffer* buf;
    float data(uint16_t index) { return buf->read_at<float>(0 + index * 4); }
    float height() { return buf->read_at<float>(16); }
    float vh()     { return buf->read_at<float>(20); }
};
typedef void (*EKFCallbackFunctionType)(EKF*, void*);
bool EKFW(float* data, float height, float vh);   // 发送（写）
// + DLX_ProtocolBuffer::check() 里多一个 case 10，收到就回调
```

要点：

1. **支持的基本类型**：`stdint` 全套（UINT8/16/32、INT8/16/32）+ `FLOAT` + `DOUBLE`；
2. **支持定长数组**（`@FixedLength(n)`）与**变长字段**（见下面的 `SimpleLog`）；
3. 每个类在生成时**自动分配一个类型号**（`head >> 5 & 0x3ff`），收端靠这个类型号分辨数据体；
4. **头部自带 CRC**（见 §2），收到坏帧直接丢，不用业务层校验；
5. 每个类同时生成"写"函数（`XxxW(...)`）和"读"包装（`struct Xxx` + getter + 回调注册 `setXxxCallbackFunction`）。

## 2. 帧格式

```
[ head: 2 字节, 大端(网络序) ][ payload: N 字节 ]
```

`head` 的位定义（`DLX_ProtocolBuffer` 里的 `dlx_header`）：

| 位 | 含义 |
| --- | --- |
| bit15 | 恒为 1：帧起始标志 |
| bit14..5 | `type`（10 bit，报文类型号） |
| bit4..1 | `crc4 = crc4_itu(payload) & 0xF` |
| bit0 | 恒为 0 |

所以 `head = (1<<15) | (type<<5) | (crc4<<1)`，写成两个字节时**高字节先发**。

CRC：`crc4_itu`，初值 0，逐字节 `crc ^= byte`，再 8 次
`crc = (crc&1) ? (crc>>1)^0x0C : crc>>1`，最后取低 4 bit，**覆盖整个 payload**。

变长报文（如 `SimpleLog`）把长度放在 payload 最前面，CRC 也覆盖长度字段：

```
SimpleLog payload = [len: UINT16][len 个 INT8 字节]      // crc4 覆盖 2+len 字节
```

接收侧（`check()`）的处理顺序：先 `peek` 头 → 校验 bit15/bit0 → 按 `type` 查该报文的固定长度 →
`available() < len + 2` 就先返回（等字节攒够）→ `skip(2)` + 读出 payload → **CRC 不过就丢** →
构造 `struct Xxx` 视图 → 回调。**未知类型只 `skip(1)` 并返回**（用于重新同步）。

返回值是 `DLXCheckResult`（不再是 bool），语义按"消费没消费 + 算不算出错"两维划分：

| 返回值 | 含义 | 消费字节 | 算不算出错 |
| --- | --- | --- | --- |
| `SUCCESS` | 整帧校验通过并已回调 | `2 + len` | 否 |
| `FAILED_CRC` | 帧已整帧读出，但 CRC4 不过（丢帧） | `2 + len` | 是（帧废了） |
| `FAILED_HEAD` | bit15=0 或 bit0=1（非法帧头），或类型号未定义 | `1` | 是（重新找同步） |
| `FAILED_INSUFFICIENT` | 缓冲里不足 2 字节，或不足 `len + 2`（半帧） | `0` | **否**：只是"数据不足，下次再说" |
| `FAILED_OVERFLOW` | 变长帧长度超出解帧缓冲区 | `0` | 预留，当前生成代码不会返回 |

> 三个要点：
>
> 1. `FAILED_CRC` / `FAILED_HEAD` 是**消费了但失败**，"失败"不等于"没前进"；
>    `FAILED_INSUFFICIENT` 相反 —— **成功了但数据不足**（名字带 FAILED 有误导性），
>    正常等待半帧的情况都会走到这里，**不该当错误打日志**；
> 2. 所以"还没解完"的判据是 `!= FAILED_INSUFFICIENT`（本工程封装成
>    `flight_config_struct.hpp` 的 `drainDlx()`），循环单调推进、必然退出；
> 3. 不变式的落脚点：**只有 `FAILED_INSUFFICIENT` 可以不消费字节**。
>    `FAILED_OVERFLOW` 预留 —— 可变长帧超过缓冲区总容量属于设计失误（单片机不会
>    一次收很大的可变长帧），当前不处理。

### 3.1 字节序（重要，别踩坑）

生成代码里两类字段的处理**不一样**，写代码/对接上位机时必须照着来：

| 字段写法 | 生成代码（写 / 读） | 线上字节序 |
| --- | --- | --- |
| 标量 `val x: Float / UINT16 / UINT32 / INT32` | `buffer.write<T>(x)` / `buf->read_at<T>(o)` | **大端**（`write`/`read_at` 内部都会 `bswap`） |
| 定长数组 `float[] / uint16[]` | `buffer.write(ptr, n)` / `buf->read_le_at<T>(o + i*sizeof(T))` | **原始内存序（ARM/x86 就是小端）** |

也就是说：**标量一律大端，定长数组是原始小端**。
（`GroundCmd/GroundReply/SessionInfo/PerfMonitor` 全是标量，一律大端；
`FlightLog` 里的 `quat[]/bodyRate[]/.../motor[]` 是定长数组，按原始小端，两端都用生成代码就不会错。）

## 4. 发送 / 接收怎么用

> **构建顺序(很容易踩)：** C++ 的 `DL_LIB/dlx.hpp` 是**上位机 KSP 生成出来的**
> （`Protocol.kt` 文件头的 `@file:CppProtocolTarget("...\\DL_LIB\\dlx.hpp")`），
> 也就是说**每次构建上位机都会覆盖它**。所以正确顺序是：
> **① 改 `Protocol.kt` → ② 构建上位机(KSP 重新生成 C++/Kotlin) → ③ 再构建/烧写固件**。
> 反过来就会出现"C++ 与 Kotlin 不是同一次生成"→ 类型号/字段错位 → 命令被回 `BadArgument(status=2)`、
> 或者解析出一堆看着合法的垃圾帧。
> （本次现场就踩了这个：固件 hex 时间 0:26:12，而 `dlx.hpp` 被上位机在 0:26:58 覆盖。）

```cpp
// 发送：先把 buffer reset 到"当前帧"位置，再调协议函数，最后 DMA 发 buffer.used() 字节
dlxBuf.reset();
protocol.FlightCoreStatusW(qx, qy, qz, qw, m0, m1, m2, m3, heightOrVz, status, error);
serialDMA.reset(protocol.buffer.used());
serialDMA.start();

// 接收：解析器绑一个 RingByteBuffer(收) + 一个 ByteBuffer(解帧临时区)，主循环里反复调 check()
DLX_ProtocolBuffer proto(dmaBuf, &rxRing, &frameBuf);
proto.setControlToFlightCallbackFunction(+[](ControlToFlight* c, void* ctx) { ... }, &ctx);
while (true) { proto.check(); }
```

注意：

- `check()` **一次只处理一帧**（返回 `DLXCheckResult`，成功是 `SUCCESS`）；把积压读干净要用
  `drainDlx()`（它按"字节数有没有减少"循环），**不能**写成 `while (check() == SUCCESS)`——
  噪声字节返回的是 `FAILED_HEAD`（不是 `SUCCESS`），会让 `while` 条件为假而**立刻退出循环**：
  本轮只推进了 1 个字节，缓冲里剩下的合法帧要等下一次调用才解得到（噪声有 N 个字节就要 N 次调用）。
  后果是"晚一个轮询周期"而不是丢帧，但语义很容易写错，统一用 `drainDlx()`；
- `frame`（解帧临时区）必须**不小于最大 payload**（当前最大是 `FlightDebug` 的 136B）；
- 发送缓冲区里 `reset()` 之后由协议函数自己写头，不要把 `used()` 拿来当"已有数据"用。

## 5. 新增报文（地面模式：日志管理 + 串口调试）

需求：跳线帽接上后进入地面模式，上位机用命令做 **查会话 / 删最老 N 个会话 / 回传整个会话 /
整片格式化**，串口调试模式下还要额外回**计算负载（DWT）**。共 4 条新报文，
**Kotlin 侧定义如下**（字段顺序就是线上顺序，全部整数标量）：

```kotlin
/** 地面模式命令：上位机 -> 下位机 */
class GroundCmd(
    @TargetBasicType(DLXBasicType.UINT16) val op: Int,        // 见 Op 表
    @TargetBasicType(DLXBasicType.UINT16) val mode: Int,      // Unlock 时: 0=飞行 1=串口调试 2=日志管理
    @TargetBasicType(DLXBasicType.UINT32) val sessionId: Int, // DumpSession 指定会话号
    @TargetBasicType(DLXBasicType.UINT32) val count: Int,     // DeleteOldest: 会话个数
)

/** 地面模式应答：下位机 -> 上位机（每条命令回一条） */
class GroundReply(
    @TargetBasicType(DLXBasicType.UINT16) val op: Int,     // 回应的命令
    @TargetBasicType(DLXBasicType.UINT16) val status: Int, // 0=OK, 其它见 §5.2
    @TargetBasicType(DLXBasicType.UINT32) val sessionId: Int,
    @TargetBasicType(DLXBasicType.UINT32) val value: Int,  // 会话数 / 条目数 / 擦除块数…
)

/** 一条日志会话信息（ListSessions 时每个会话发一条，最后再回一条 GroundReply 汇总） */
class SessionInfo(
    @TargetBasicType(DLXBasicType.UINT32) val sessionId: Int,
    @TargetBasicType(DLXBasicType.UINT32) val slotCount: Int,  // 占用槽数(1 槽 = 128KB)
    @TargetBasicType(DLXBasicType.UINT32) val entryCount: Int, // 条目数量
    @TargetBasicType(DLXBasicType.UINT16) val active: Int,     // 1 = 本次上电的会话
    @TargetBasicType(DLXBasicType.UINT16) val reserved: Int,   // 该会话还能写多少条(仅 active 有意义)
)

/** 串口调试模式的负载统计（每 200ms 一条，单位：CPU 周期，168MHz） */
class PerfMonitor(
    @TargetBasicType(DLXBasicType.UINT32) val loopAvgCycle: Int,   // 主循环平均耗时
    @TargetBasicType(DLXBasicType.UINT32) val loopMaxCycle: Int,   // 主循环最大耗时
    @TargetBasicType(DLXBasicType.UINT32) val ekfCycle: Int,       // EKF 慢路径平均耗时
    @TargetBasicType(DLXBasicType.UINT32) val ctrlCycle: Int,      // 控制器+混控平均耗时
    @TargetBasicType(DLXBasicType.UINT32) val logCycle: Int,       // 日志(打包/写 flash)平均耗时
    @TargetBasicType(DLXBasicType.UINT32) val ioCycle: Int,        // IMU FIFO + 气压计读取平均耗时
    @TargetBasicType(DLXBasicType.UINT16) val samples: Int,        // 本统计窗口的循环次数
    @TargetBasicType(DLXBasicType.UINT16) val drops: Int,          // 本窗口内丢弃的日志条数
)
```

### 5.1 `GroundCmd.op` 取值

| op | 名称 | 参数 | 行为 |
| --- | --- | --- | --- |
| 1 | `Unlock` | `mode` | 地面模式"解锁"：进入 `mode` 指定的模式（0 飞行 / 1 串口调试 / 2 日志管理） |
| 2 | `ListSessions` | — | 先按时间从旧到新发 `SessionInfo`，再回 `GroundReply(op=2, value=会话数)` |
| 3 | `DeleteOldest` | `count` | 丢掉**最老**的 `count` 个会话（环形队列语义，腾出的槽并入当前会话） |
| 4 | `DumpSession` | `sessionId` | 把这个会话的日志条目**整会话**按原始日志帧流回传 |
| 5 | `FormatFlash` | — | 整片擦除重建（几十秒，会丢日志+参数），随后重新初始化 |
| 6 | `Ping` | — | 回一条 `GroundReply(op=6, status=0)`，用于探测链路 |

### 5.2 `GroundReply.status` 取值

| status | 含义 |
| --- | --- |
| 0 | OK |
| 1 | 未知命令 |
| 2 | 参数非法 |
| 3 | Flash 操作失败 |
| 4 | 找不到指定会话 / 条目 |
| 5 | 忙（正在擦除等） |

### 5.3 兼容旧 `UnBlock`

type 1 `UnBlock`（1 字节 `param`）在地面模式下也接受，等价于 `Unlock(mode = param)`：
`param` 1 → 串口调试，2 → 日志管理（保持与首飞版本的操作习惯一致）。

### 5.4 这 4 个类怎么加进 KSP（已加）

字段顺序就是线上顺序，重新生成 `dlx.hpp` 即可：

```kotlin

```

下位机侧就用生成出来的东西（与 NRF 那套一模一样）：

```cpp
protocol.GroundReplyW(op, status, sessionId, value);      // 发
protocol.SessionInfoW(sessionId, slotCount, entryCount, active, reserved);
protocol.PerfMonitorW(...);
protocol.setGroundCmdCallbackFunction(onGroundCmd, ctx);  // 收
protocol.setUnBlockCallbackFunction(onUnBlock, ctx);      // 收(旧版)
drainDlx(protocol, rxRing);                               // 解帧, 走回调(见 §4)
```

> 这 4 个类已经加进 KSP 并生成进 `dlx.hpp`（类型号 11~14，见 §3 表）。
> 下位机只用生成出来的 `GroundCmdW/GroundReplyW/SessionInfoW/PerfMonitorW` 与
> `setGroundCmdCallbackFunction()`；`GroundReply/SessionInfo/PerfMonitor` 是单向（只发），
> 生成器不会为它们产生接收结构体与回调，这是正常的。

一个使用细节：`check()` 遇到噪声字节只吞 1 个字节并返回 `FAILED_HEAD`，遇到半帧则
一个字节都不动并返回 `FAILED_INSUFFICIENT`，所以外面要套一层"看 `available()` 有没有减少"
的循环（本工程封装成 `flight_config_struct.hpp` 的 `drainDlx()`）。

## 6. 日志流格式（flash 回传 / 串口调试共用）

> **铁律：这条串口上只能有 DLX 帧。**
> 任何"人类可读文本"（启动横幅、命令回显、错误提示）都必须打成 `SimpleLog`（类型 0）帧，
> 不能直接 `usart1.send()` 发 ASCII —— 上位机是按帧解析的：直接把 `"[Boot] ..."` 发出去，
> 它会读到 `5b42`(=`'[' 'B'`)、`6f6f`(=`'oo'`)、`745d`(=`'t]'`) 这种"帧头"，
> 屏幕/控制台就会刷 `Header错误xxxx` / `未知Header,可能没有对齐xxxx`，而且一旦错位
> （生成代码每次只前进 2 字节）很难自己恢复，得靠"先连上位机、再解锁"重新从帧边界开始。
> 本工程的做法：`flight_config_struct.hpp` 里的 `logLine()` 把文本补齐成偶数长度后
> 用 `protocol.SimpleLogW()` 发出去，上位机 `simpleLogListener` 显示在屏幕上。
>
> **另一个更隐蔽的坑（曾经把 MCU 卡死）：** `DMA::init()` 结尾会 `DMA_ClearFlag(TC)`，
> 而 `DMA::wait()` 是 `while (TC == RESET);` —— **没启动过传输就 `wait()` 会死等**。
> 旧版 `main_final_test.cpp` 是在 `setDMASend()` 之后先 `start()` 一次把 TC 置起来才进循环，
> 所以没暴露。现在统一用 `flight_config_struct.hpp` 里的 `serialDmaBusy()` 标记：
> **只有自己 `start()` 过的传输才允许 `wait()`**（`dmaSendStart()` / `flushSerial()` / 日志线程都遵循）。
> 症状识别：上电后 LED 不再心跳、串口一个字都不出 → 十有八九是卡在某个 `wait()` 上。

**回传和调试流都按 DLX 的 `FlightLog` 报文发**，上位机用生成代码解析，不用手写字节日志偏移：

```kotlin
class FlightLog(                       // 类型号 15, 负载 140 字节
    @TargetBasicType(DLXBasicType.UINT32) val sessionId: Int,   // 0 = 不是从 flash 里读的(调试流)
    @TargetBasicType(DLXBasicType.UINT32) val seq: Int,         // flash: 会话内序号; 调试流: 自增
    @TargetBasicType(DLXBasicType.UINT32) val tickMs: Int,
```

- 一条日志 = 一帧：`[head 2B][负载 140B]`，共 142 字节，CRC4 覆盖负载；
- **flash 里存的仍是 `dlx::LogEntry`**（POD，144B 业务+管理器，CRC16，掉电安全，几何不变）；
  回传时现场转成 `FlightLog` 帧（`writeLogEntry()`），所以既省 flash 校验又让上位机解析省事；
- 两条链路同一个格式：**飞行模式**把 POD 写 flash；**串口调试**直接把 POD 转 `FlightLog` 发串口；
  **日志管理回传**读 flash 再转 `FlightLog` 发串口；
- 调试模式下同一路串口还会有 `PerfMonitor`（类型 14）——按类型号分流即可；
- 一条日志的字段含义见 `DL_LIB/W25Q128/dlx_flash_manager_config.h` 的 `LogEntry` 注释。
